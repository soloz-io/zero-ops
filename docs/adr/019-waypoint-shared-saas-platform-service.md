## Context

The Waypoint Builder is a workflow automation SaaS — a visual state machine designer that compiles blueprints into durable Vercel Workflows SDK executions. It was initially designed with a per-tenant deployment topology (ADR-017): one SDK pod and one runtime database per platform tenant per Spoke cell.

This model created unsustainable operational overhead:

- **Pod sprawl**: `N tenants × M cells` SDK deployments, each with independent lifecycle management
- **Schema duplication**: the `workflow.*` schema (8MB+) replicated per tenant database
- **Provisioning coupling**: onboarding a new platform tenant to Waypoint required provisioning a new K8s namespace, a new database, and new secret injection — a per-tenant infrastructure operation
- **Secret delivery mismatch**: ADR-018's init-mode Infisical injection assumed one pod per tenant; it cannot support per-tenant credential isolation in a shared pod

Waypoint is not meaningfully different from other platform services like ArgoCD, Infisical, or KAgent — it is a shared capability consumed by platform tenants, not a tenant-specific runtime. The correct deployment model is one shared instance per Spoke cell.

---

## Decision

**Waypoint is provisioned as a single platform-level tenant in the fleet-registry**, deploying one shared instance per Spoke cell that serves all platform tenants.

### Deployment Topology

```
Spoke Cell (e.g. spoke-pool-eu-prod-01)
  namespace: tenant-waypoint
    waypoint-bff        (1 Deployment — multi-tenant Control Plane API)
    waypoint-frontend   (1 Deployment — shared UI)
    waypoint-sdk        (1 Deployment — tenant-agnostic execution engine)
    waypoint-db         (1 PostgreSQL — single workflow.* schema, OSS as-is)
```

Waypoint is provisioned via a single `fleet-registry/tenants/waypoint/values.yaml` entry — the same fleet-registry pattern used by all tenants. The `AINativeSaaS` XR provisions the namespace, CNPG database, resource quotas, and KAgent exactly as for any other tenant.

### Database Ownership

| Database | Env Var (BFF) | Env Var (SDK) | Contents |
|----------|--------------|--------------|----------|
| Control Plane DB (`waypoint_control_plane`) | `DATABASE_URL` | `CONTROL_PLANE_DATABASE_URL` | blueprints, blueprint_deployments, plugins, workflow_runs (control), workflow_hooks (RBAC), agent_prompts |
| Runtime DB (`waypoint_runtime`) | `SDK_DATABASE_URL` | `DATABASE_URL` + `WORKFLOW_POSTGRES_URL` | Vercel world-postgres tables: workflow_runs, workflow_events, workflow_steps, workflow_hooks, workflow_stream_chunks |

The `world-postgres` OSS package is used **without modification**. The runtime DB is a single shared database — the OSS design intent — with no `tenant_id` added to engine tables.

Tenant identity is enforced at the **BFF trust boundary**: every `blueprints`, `blueprint_deployments`, `workflow_runs`, and `workflow_hooks` row in the control-plane DB carries `tenant_id`. The SDK receives and stores only execution state; it is tenant-agnostic by design.

### Plugin Credential Resolution

ADR-018's init-mode pod injection is replaced with **runtime context resolution**.

The compiled blueprint bundle (generated by `packages/bff/src/blueprint-bundler.ts`) inlines `packages/waypoint-sdk/src/steps.ts` via esbuild. The `executePlugin` step function — which runs inside the VM sandbox — receives `tenantId` and `cellId` as part of the `WorkflowContext` and resolves credentials from Infisical at call time:

```typescript
// WorkflowContext (generated by blueprint-compiler.ts)
export interface WorkflowContext {
  recordId: string;
  tenantId: string;   // ← added
  cellId: string;     // ← added
}

// executePlugin (waypoint-sdk/src/steps.ts)
export async function executePlugin(
  pluginId: string,
  input: Record<string, unknown>,
  context: { tenantId: string; cellId: string }
): Promise<Record<string, unknown>> {
  'use step';
  // Resolve from Infisical at call time using tenant-scoped path
  const apiKey = await resolvePluginCredential(
    context.cellId,
    context.tenantId,
    pluginId
  );
  // ...call plugin endpoint
}
```

**Infisical path convention** (carried forward from ADR-018):
```
/spoke-pool/{cellId}/tenants/{tenantId}/plugins/PLUGIN_{ID}_API_KEY
/spoke-pool/{cellId}/tenants/{tenantId}/plugins/PLUGIN_{ID}_ENDPOINT
```

**Isolation enforcement:** The shared SDK pod holds a single Infisical Machine Identity scoped to the `tenant-waypoint` namespace. It requests tenant-specific secret paths at runtime. Infisical's path ACL ensures the SDK can only read paths it is authorised for. No tenant's credentials are present in `process.env` of the shared pod.

**Credential caching:** Resolved credentials are cached in-process with a TTL (configurable, default 5 minutes) to minimise Infisical API calls under load. Cache keys are `tenantId:pluginId`. TTL expiry triggers a fresh Infisical fetch on next execution.

### Code Change Scope

Only files within the Waypoint monorepo change. Zero changes to OSS packages:

| File | Change |
|------|--------|
| `packages/waypoint-sdk/src/steps.ts` | `executePlugin` accepts `context: { tenantId, cellId }`, resolves credentials from Infisical at runtime via TTL cache |
| `packages/bff/src/blueprint-compiler.ts` | `WorkflowContext` gains `tenantId` and `cellId`; `plugin` case emits `executePlugin(id, inputs, { tenantId: ctx.tenantId, cellId: ctx.cellId })` |
| `fleet-registry/tenants/waypoint/values.yaml` | New tenant descriptor (single entry, provisions the shared Waypoint instance) |

### Fleet Registry Descriptor

```yaml
# fleet-registry/tenants/waypoint/values.yaml
tenantId: waypoint
tier: enterprise
cellId: spoke-pool-eu-prod-01

database:
  name: tenant-waypoint-db
  migrations:
    baseline:
      gitRepo: "https://github.com/soloz-io/zero-ops"
      gitRevision: "main"
      gitPath: "migrations/tenant-baseline"
    tenantSpecific:
      gitRepo: "https://github.com/soloz-io/fleet-registry"
      gitRevision: "main"
      gitPath: "tenants/waypoint/migrations"

resourceQuota:
  cpu: "4000m"
  memory: "8Gi"
  storage: "20Gi"
  pods: "20"

ownerEmail: "platform@soloz.io"
```

The runtime DB (`waypoint_runtime`) and control-plane DB (`waypoint_control_plane`) are both provisioned on the Spoke via the standard `TenantDatabase` XR pattern. Two `TenantDatabase` XRs are created for the `waypoint` tenant — one for each database — matching the dual-DB ownership constraint enforced by `validateSdkRuntimeBoundary()` and `validateBackendRuntimeBoundary()`.

## Consequences

### Positive

- **Operational simplicity**: One set of Waypoint pods per cell regardless of how many platform tenants use it. Onboarding a new tenant to Waypoint requires only a BFF-level registration — no new K8s namespace, no new runtime database, no new pod.
- **OSS compatibility preserved**: `world-postgres` used completely unmodified. Single runtime database is its intended use case.
- **Clean trust boundary**: BFF enforces all tenant scoping. SDK is a pure execution engine — stateless with respect to tenant identity.
- **Secret isolation without pod sprawl**: Infisical path ACL provides per-tenant credential isolation without requiring per-tenant pods. The ADR-018 security model (path-scoped Machine Identity) is preserved; only the delivery mechanism changes from pod-startup injection to runtime resolution.
- **No Kubernetes namespace proliferation**: Waypoint no longer contributes N × M namespaces to the cluster.

### Trade-offs

- **Runtime Infisical dependency**: Plugin credential resolution now requires a live Infisical call on first execution (after cache miss). This adds latency (~50-200ms) on cold starts. Mitigated by TTL cache and Infisical HA deployment.
- **Shared runtime DB**: All workflow execution state is in one database. A schema corruption or CNPG failure affects all tenants simultaneously. Mitigated by CNPG HA with streaming replication and automated failover.
- **No database-level tenant isolation for runtime state**: Workflow runs for all tenants coexist in `workflow.workflow_runs`. Tenant separation relies entirely on BFF query-level filtering (`WHERE tenant_id = $1`). This is acceptable: the workflow engine tables do not contain business data — only execution state (status, hooks, steps). Business data remains in tenant-scoped tables in the control-plane DB.

### Boundary Rules

- ✅ One Waypoint deployment per Spoke cell (not per platform tenant)
- ✅ BFF enforces `tenant_id` scoping on all control-plane DB reads and writes
- ✅ SDK is tenant-agnostic — no `tenant_id` in runtime DB tables
- ✅ Plugin credentials resolved at runtime via Infisical with `tenantId` + `cellId` context
- ✅ Infisical path convention `/spoke-pool/{cellId}/tenants/{tenantId}/plugins/*` retained
- ✅ `world-postgres` used without modification or fork
- ✅ Two databases provisioned per Waypoint deployment (control-plane DB + runtime DB)
- ❌ Do NOT add `tenant_id` to `workflow.*` tables — this would require forking world-postgres
- ❌ Do NOT share `process.env` plugin credentials across tenants in the SDK pod
- ❌ Do NOT deploy a Waypoint SDK pod per platform tenant — this reverts to the ADR-017 model
- ❌ Do NOT use init-mode Infisical injection for plugin secrets in the shared pod model
