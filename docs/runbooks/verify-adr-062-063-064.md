# Verifying ADR-062, ADR-063 and ADR-064

The order matters: 063 publishes the charts that 064 pins, and 062 scaffolds the
repository that would carry the pin for a tenant.

## 0. Prerequisites

```bash
export HCLOUD_TOKEN=$(cat k8-secrets/hetzner/token)
git push -u origin feature/startup-os-onboarding
```

ArgoCD reconciles the branch from GitHub, not from the working tree. Anything
unpushed is invisible to the cluster, and the failure it produces is a stale
cached render rather than an error naming the missing commit.

## 1. ADR-063 — the bundle is published as versioned charts

```bash
git tag v0.1.0 && git push origin v0.1.0
gh run watch                       # publish-platform-charts
```

The workflow packages every platform-owned component, asserts each renders
exactly what ArgoCD applies today, and pushes to
`oci://ghcr.io/soloz-io/charts`.

Passes when:

- the run is green, and its summary lists the packaged charts;
- `hub-gateway` is refused, naming its `generated/` directory. That refusal is
  the decision working: the component carries per-cluster instance data, and
  publishing it would hand every cluster one cluster's values;
- the packages are **public**. ADR-063 requires a tenant to be able to mirror
  what it runs without asking permission, which a private registry contradicts,
  and ArgoCD has no OCI credential.

```bash
helm show chart oci://ghcr.io/soloz-io/charts/platform-namespaces --version 0.1.0
```

## 2. ADR-064 — the version is pinned per cluster

`platform-namespaces` and `platform-capi-resources` consume their published
charts. Both are leaf components, so a failure is contained to them.

```bash
./scripts/hub-bootstrap.sh \
  --name=hub-hybrid-dev --provider=hybrid --region=hel1 \
  --environment=dev --topology= \
  --home-worker-enabled --tailnet-name=taila4c44b.ts.net
```

Passes when, on the built cluster:

```bash
kubectl -n platform-ops get application platform-namespaces \
  -o jsonpath='{.spec.source.repoURL} {.spec.source.chart} {.spec.source.targetRevision}{"\n"}'
# oci://ghcr.io/soloz-io/charts platform-namespaces 0.1.0
```

and a component that was not flipped still resolves the other way:

```bash
kubectl -n platform-ops get application platform-cloudnative-pg \
  -o jsonpath='{.spec.source.repoURL} {.spec.source.targetRevision}{"\n"}'
# https://github.com/soloz-io/zero-ops feature/startup-os-onboarding
```

Both branches resolving is the point. One value on the seed decides which
published bundle this cluster runs; nothing the component declares does.

## 3. ADR-062 — onboarding scaffolds a tenant

```bash
go run ./cmd/hub tenant scaffold --dry-run \
  --tenant acme --org soloz-io --domain acme.example --out /tmp/acme-gitops
```

Renders locally and creates nothing. Check before the real run: the hydrated
`clusters/acme-hub/` carries no tokens, and `templates/spoke-cluster/` still
does — that directory is what the tenant renders for its NEXT cluster, and a
copy hard-coded to the first one would collide with it.

```bash
go run ./cmd/hub tenant scaffold \
  --tenant acme --org soloz-io --domain acme.example
```

Passes when `soloz-io/acme-gitops` exists, holds one commit, and carries a
version and values per cluster and none of the platform's content.

## What is not covered

The promotion pull request of ADR-064 is not built: a bundle version is pinned
per cluster and changed by hand, not proposed. Everything else in that ADR --
where the version lives, that it is per cluster, that promoting is a change to
one field -- is exercised above.
