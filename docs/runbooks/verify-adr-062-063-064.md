# Verifying ADR-062, ADR-063 and ADR-064

The order matters: 063 publishes the charts that 064 pins, and 062 scaffolds the
repository that would carry the pin for a tenant.

## 0. Prerequisites

```bash
export HCLOUD_TOKEN=$(cat k8-secrets/hetzner/token)
git push -u origin feature/startup-os-onboarding
go run ./cmd/hub bundle-version     # expect: development
```

`development` is the answer you want here. It means no version was injected,
which is what an ordinary build is, and under ADR-068 platform content is then
reconciled from the branch you just pushed. Nothing needs tagging to be tested.

ArgoCD reconciles the branch from GitHub, not from the working tree. Anything
unpushed is invisible to the cluster, and the failure it produces is a stale
cached render rather than an error naming the missing commit.

## 1. ADR-063 — the bundle is published as versioned charts

Publishing is a GitHub Release, not a tag push: a tag can be created and moved,
where a release is a deliberate act with an author and a record.

```bash
gh release create v0.1.0 --generate-notes
gh run watch                       # publish-platform-charts
```

The workflow packages every platform-owned component, asserts each renders
exactly what ArgoCD applies today, and pushes to
`oci://ghcr.io/soloz-io/charts`.

Passes when:

- the run is green, and its summary lists the packaged charts;
- `hub-gateway` is refused, naming its `generated/` directory. That refusal is
  the decision working: the component carries per-cluster instance data, and
  publishing it would hand every cluster one cluster's values;
- the packages are **public**. ADR-063 requires a tenant to be able to mirror
  what it runs without asking permission, which a private registry contradicts,
  and ArgoCD has no OCI credential;
- the release carries `hub-linux-amd64` and its siblings. One run publishes the
  bundle and the build that requests it, and the workflow refuses to finish if
  that build does not report the version it was injected with.

```bash
helm show chart oci://ghcr.io/soloz-io/charts/platform-namespaces --version 0.1.0
```

## 2. ADR-064 — the version is pinned per cluster

The bootstrap below runs a development build, so its components reconcile from
the branch. That is the mode being tested here: what ADR-064 asks is that the
version a cluster runs is the cluster's own and survives a re-seed.

```bash
./scripts/hub-bootstrap.sh \
  --name=hub-hybrid-dev --provider=hybrid --region=hel1 \
  --environment=dev --topology= \
  --home-worker-enabled --tailnet-name=taila4c44b.ts.net
```

Passes when the seed records the version and components resolve from the branch:

```bash
kubectl -n platform-ops get application platform-boundaries \
  -o jsonpath='{range .spec.source.helm.parameters[?(@.name=="bundleVersion")]}{.value}{"\n"}{end}'
# development

kubectl -n platform-ops get application platform-cloudnative-pg \
  -o jsonpath='{.spec.source.repoURL} {.spec.source.targetRevision}{"\n"}'
# https://github.com/soloz-io/zero-ops feature/startup-os-onboarding
```

Then check the part that was a live bug — a re-seed must not move the version:

```bash
kubectl -n platform-ops patch application platform-boundaries --type=json \
  -p '[{"op":"replace","path":"/spec/source/helm/parameters/N/value","value":"0.1.0"}]'  # N = bundleVersion's index
go run ./cmd/hub reseed --kubeconfig k8-secrets/kubeconfig/hub-hybrid-dev.kubeconfig
```

Passes when the seed still reads `0.1.0` and the CLI says it is leaving the
cluster's version alone. A development build re-asserting its own version here
would be a silent downgrade of a promoted cluster.

To see the released path, bootstrap with an injected build once a release
exists:

```bash
go run -ldflags "-X github.com/soloz-io/zero-ops/internal/hub-cli/versions.BundleVersion=0.1.0" \
  ./cmd/hub bundle-version   # 0.1.0, and platform components then resolve to the registry
```

## 3. ADR-062 — onboarding scaffolds a tenant

```bash
go run ./cmd/hub tenant scaffold --dry-run \
  --tenant acme --org soloz-io --domain acme.example --out /tmp/acme-gitops
```

Renders locally and creates nothing. Check before the real run: the hydrated
`clusters/acme-hub/` carries no tokens, and `templates/spoke-cluster/` still
does — that directory is what the tenant renders for its NEXT cluster, and a
copy hard-coded to the first one would collide with it.

```bash
go run ./cmd/hub tenant scaffold \
  --tenant acme --org soloz-io --domain acme.example
```

Passes when `soloz-io/acme-gitops` exists, holds one commit, and carries a
version and values per cluster and none of the platform's content.

## What is not covered

The promotion pull request of ADR-064 is not built: a bundle version is changed
by hand, not proposed. Everything else in that ADR -- where the version lives,
that it is the cluster's own, and that a re-seed cannot move it -- is exercised
above.

Boundary 02 reconciles from Git in both modes. Its paths are a function of the
provider, which ADR-061 gives as the reason they are not descriptors, so
publishing them needs a chart per component that selects its provider from a
value. Until then a released cluster still reaches for the platform repository
and the portability ADR-063 asks of a bundle is not yet whole.

Descriptors are still read from this repository by a git generator, so the same
is true of them (recorded in ADR-063).
