That’s a solid and very pragmatic decision. Aligning with Supabase over Neon is exactly what many teams do when they want:
	•	faster time to production
	•	simpler mental model
	•	strong GitOps compatibility

But to do this correctly and idiomatically, we need to be precise about what “Supabase-style” actually means — because it’s often misunderstood.

⸻

🧠 What “Supabase Model” REALLY Means

It is NOT:

“Everything is in Git and magically applied”

It is:

Declarative schema + migration engine + control plane execution

⸻

🔑 Core Principle

Git (SQL) = Source of Truth for schema
Control Plane = Executes and reconciles
Database = Stores actual state


⸻

🏗️ Your Target Architecture (Supabase-Aligned)

1. Source of Truth → Declarative SQL

You define tenant structure like:

-- migrations/tenant_base.sql
CREATE SCHEMA IF NOT EXISTS {{tenant_id}};

CREATE TABLE {{tenant_id}}.users (...);

ALTER TABLE {{tenant_id}}.users ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation
ON {{tenant_id}}.users
USING (tenant_id = current_setting('app.tenant_id'));


⸻

2. Control Plane Applies It

Your MCP / provisioning service:
	•	substitutes {{tenant_id}}
	•	runs migrations
	•	tracks applied state

⸻

3. Database Stores Reality
	•	schemas exist
	•	RLS enforced
	•	data persists

⸻

🔁 How Provisioning Works Now

Tenant Create Flow

1. MCP receives request
2. Writes tenant metadata (DB)
3. Picks cluster
4. Runs migration engine:
   → creates schema
   → applies base schema
   → applies RLS
5. Stores connection config


⸻

Replay / Recovery

If cluster is recreated:

1. Restore DB (preferred)
2. If missing:
   → replay migrations for each tenant


⸻

🔥 The MOST IMPORTANT RULE

❗ Migrations must be idempotent and replayable

Example:

CREATE SCHEMA IF NOT EXISTS tenant_123;

NOT:

CREATE SCHEMA tenant_123; -- ❌ breaks on replay


⸻
