# Per-Tenant Database User — Architecture Decision

**Status**: APPROVED — READY FOR IMPLEMENTATION (v4)
**Date**: 2026-04-22  
**Context**: Issue #44 — Shared `app` user violates tenant isolation (FR-4.6)

---

## 1. Requirement

**FR-4.6** requires each tenant to have a dedicated PostgreSQL user with:
- Unique randomly-generated password (32 chars)
- GRANT permissions only on their own database (`tenant-<id>-db`)
- Credentials stored in a Kubernetes Secret in the tenant namespace
- Pooler and PostgREST connecting via tenant-specific credentials
- Shared `app` user NOT used for tenant workloads

---

## 2. The Problem

### What we tried
Crossplane `provider-sql` on the Hub to create `Role` and `Grant` CRs per tenant.

### Why it failed
`provider-sql` runs on the **Hub cluster** but needs to connect to PostgreSQL on the **Spoke cluster**. The Spoke's `shared-cnpg-rw` is a `ClusterIP` service — not reachable cross-cluster. There is no network path from Hub to Spoke's port 5432.

### Why the other options fail

| Option | Why it fails |
|---|---|
| CNPG `spec.managed.roles` | Requires patching the same shared `Cluster` array for every tenant. 50 concurrent tenants = race conditions, state overwrites, etcd contention. |
| Atlas migration `CREATE USER` | Fatal chicken-and-egg: AtlasMigration connects *as* the tenant user. If Atlas creates the user, it can't connect to run the migration in the first place. |
| Expose CNPG via LoadBalancer | Exposes a multi-tenant database externally. Violates zero-trust model. |

---

## 3. The Idiomatic Solution: Remote Provider Pattern + TenantDatabase Abstraction

### Core Principle

> Hub manages **intent** (platform API). Spoke manages **implementation** (DB, roles, grants).

The Hub pushes a single high-level `TenantDatabase` CR to the Spoke's API server via `provider-kubernetes` (which already works cross-cluster). The Spoke's local Crossplane expands it into `Database` + `Role` + `Grant` using its own Composition — with `provider-sql` running locally against `shared-cnpg-rw` (no network boundary).

### Why not push Role/Grant directly from Hub

Pushing `Role` + `Grant` individually from the Hub couples the Hub to PostgreSQL internals. If CNPG is replaced or the grant model changes, the Hub Composition must change. With `TenantDatabase` as the abstraction:
- Hub only knows about `TenantDatabase` — a platform concept
- Spoke owns the PostgreSQL implementation details
- Swap CNPG for another DB later without touching Hub

---

## 4. Architecture

```
Hub Cluster
├── AINativeSaaS Composition
│   └── provider-kubernetes Object → TenantDatabase CR (pushed to Spoke API server)
│       └── readinessChecks: wait for TenantDatabase Ready=True before Hub Object is Ready
│
└── provider-kubernetes (existing, already works cross-cluster)

Spoke Cluster
├── Crossplane (local)
├── provider-sql (new, local — connects to shared-cnpg-rw locally, no network boundary)
├── TenantDatabase Composition (new)
│   ├── CNPG Database CR          → creates tenant-<id>-db
│   ├── provider-sql Role CR      → creates tenant-<id>-user (password from K8s Secret)
│   ├── provider-sql Grant CR     → CONNECT on tenant-<id>-db
│   ├── provider-sql Grant CR     → ALL on public tables
│   ├── provider-sql Grant CR     → ALL on public sequences
│   ├── Kubernetes Secret         → tenant-<id>-db-credentials (generated by Crossplane)
│   ├── ESO PushSecret (MANDATORY) → pushes Secret to Infisical (durable backup)
│   └── ESO ExternalSecret        → pulls from Infisical on cluster rebuild (disaster recovery)
└── shared-cnpg-rw (local ClusterIP — no cross-cluster needed)
```

---

## 5. Secret Management

### Why Infisical backup is mandatory

If the Spoke cluster is rebuilt or etcd is wiped, all K8s Secrets are lost. Without a backup:
- Crossplane reconciles and generates a **new random password**
- The DB still has the **old password** → authentication failure
- Pooler and PostgREST cannot connect → tenant is broken with no recovery path

Infisical is the durable backup. On cluster rebuild, ESO pulls the last known good credential from Infisical — the DB password still matches and tenants recover automatically.

### Flow

```
Spoke Crossplane (TenantDatabase Composition)
    ↓
Generates random 32-char password via function-patch-and-transform
    ↓
Writes directly to K8s Secret: tenant-<id>-db-credentials
    ↓
provider-sql Role CR uses Secret immediately (passwordSecretRef)
Pooler references Secret via authQueryUser.secretRef
PostgREST references Secret via PGRST_DB_URI
    ↓
ESO PushSecret (MANDATORY) mirrors Secret up to Infisical  ← DURABLE BACKUP
```

### Cluster rebuild / disaster recovery flow

```
Spoke cluster rebuilt (etcd wiped, all Secrets lost)
    ↓
Crossplane reconciles TenantDatabase XR
    ↓
Crossplane detects Secret missing → would generate NEW random password
    ↓
ESO PullSecret runs FIRST (higher sync wave than Crossplane reconciliation)
    ↓
Pulls existing credential from Infisical → restores K8s Secret
    ↓
Crossplane sees Secret already exists → skips password regeneration
    ↓
provider-sql reconciles Role → DB password still matches → tenants recover
```

**Critical ordering**: ESO must restore the Secret from Infisical before Crossplane attempts to reconcile the Role. This is enforced via sync wave ordering in the TenantDatabase Composition.

### Secret structure

```yaml
Secret name:      tenant-<id>-db-credentials
Namespace:        tenant-<id>
Fields:
  username:       tenant-<id>-user
  password:       <random 32-char alphanumeric>
  database:       tenant-<id>-db
  host:           shared-cnpg-rw.spoke-pool-system.svc.cluster.local
  port:           5432
```

### Infisical path

```
/spoke-pool/<cell-id>/tenants/<tenant-id>/db-credentials
```

### ESO PushSecret (write to Infisical)

```yaml
apiVersion: external-secrets.io/v1alpha1
kind: PushSecret
metadata:
  name: tenant-<id>-db-credentials-push
  namespace: tenant-<id>
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: infisical-cluster-secret-store
    kind: ClusterSecretStore
  selector:
    secret:
      name: tenant-<id>-db-credentials
  data:
  - match:
      secretKey: password
      remoteRef:
        remoteKey: /spoke-pool/<cell-id>/tenants/<tenant-id>/db-credentials
        property: password
```

### ESO ExternalSecret (pull from Infisical on rebuild)

```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: tenant-<id>-db-credentials-pull
  namespace: tenant-<id>
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: infisical-cluster-secret-store
    kind: ClusterSecretStore
  target:
    name: tenant-<id>-db-credentials
    creationPolicy: Merge   # Only fills missing fields, won't overwrite if Secret exists
  data:
  - secretKey: password
    remoteRef:
      key: /spoke-pool/<cell-id>/tenants/<tenant-id>/db-credentials
      property: password
```

### Dedicated DB admin role for ProviderConfig (least-privilege)

The `ProviderConfig` on the Spoke must NOT use the shared `app` user. A dedicated `crossplane_admin` role is created once per Spoke Pool during cell bootstrap:

```sql
-- Requires CREATEDB (creates tenant databases) and CREATEROLE (creates tenant users)
CREATE ROLE crossplane_admin WITH LOGIN CREATEDB CREATEROLE PASSWORD '<from-infisical>';
```

- `CREATEDB` — required because tenant databases (`tenant-<id>-db`) are created dynamically
- `CREATEROLE` — required to create per-tenant roles and execute GRANT statements
- No access to tenant data — `crossplane_admin` cannot read rows in any tenant database

Stored in Infisical at `/spoke-pool/<cell-id>/crossplane-admin-credentials`.
ESO syncs to `crossplane-admin-credentials` Secret in `spoke-pool-system` namespace.
`ProviderConfig` references this Secret.

## 6. Lifecycle and Ownership

### Tenant creation
1. Hub Composition creates `TenantDatabase` CR on Spoke via provider-kubernetes
2. Spoke Composition reconciles: creates Database → Role → Grants → Secret (via ESO/Infisical)
3. `deletionPolicy: Delete` on all composed resources — clean cascade on XR deletion

### Tenant deletion
1. Hub deletes `AINativeSaaS` XR
2. Hub Composition deletes `TenantDatabase` Object on Spoke
3. Spoke Composition finalizers clean up: Grants revoked → Role dropped → Database deleted → Secret deleted from Infisical

### Drift recovery
- `provider-sql` on Spoke continuously reconciles Role/Grant state
- If role is manually dropped: provider-sql detects drift, re-executes `CREATE ROLE`
- If grant is revoked: provider-sql re-executes `GRANT`
- Fully declarative — no manual intervention needed

---

## 7. Scaling Safeguards

At 50+ concurrent tenant provisioning:
- Each `TenantDatabase` XR is independent — no shared mutable array (unlike CNPG managed roles)
- provider-sql reconciliation is per-XR, not global
- Crossplane's built-in exponential backoff handles transient DB load spikes
- If DB connection saturation becomes an issue: tune `provider-sql` DeploymentRuntimeConfig with `--max-reconcile-rate` flag

## 8. Sync Wave Ordering and Readiness Propagation

`TenantDatabase` must be fully Ready (DB + Role + Grants provisioned) before `AtlasMigration` runs — Atlas connects as the tenant user.

### The readiness propagation problem

When the Hub uses `provider-kubernetes` to push `TenantDatabase` to the Spoke, the Hub's `Object` resource reports `Ready` the moment the CR is **written** to the Spoke's API server — not when the Spoke finishes reconciling it. Without an explicit readiness check, ArgoCD could trigger Wave 2 (AtlasMigration) before the database user exists.

### The fix: `readinessChecks` on the provider-kubernetes Object

In the Hub's `AINativeSaaS` Composition, configure `readinessChecks` on the `TenantDatabase` Object to wait for the remote XR's `Ready` condition to be `True`:

```yaml
# In ainativesaas-starter-hetzner.yaml (Hub Composition)
- name: tenant-database-remote
  base:
    apiVersion: kubernetes.crossplane.io/v1alpha2
    kind: Object
    spec:
      forProvider:
        manifest:
          apiVersion: nutgraf.in/v1alpha1
          kind: TenantDatabase
          # ...
      readinessChecks:
      - type: MatchCondition
        matchCondition:
          type: Ready
          status: "True"
  # patches...
```

This ensures the Hub's `AINativeSaaS` XR only becomes `Ready=True` after the Spoke's `TenantDatabase` is fully reconciled (DB created, Role created, Grants applied). ArgoCD's Wave 2 health gate is then correctly enforced.

### Wave ordering (unchanged)

- Wave 1: `AINativeSaaS` XR — waits for `TenantDatabase` Ready via `readinessChecks`
- Wave 2: `AtlasMigration` CR — only starts after Wave 1 health check passes

## 9. Credential Rotation

> **Note**: Rotation is a Day 2 operational concern. It does not block the current implementation. The bootstrap pipeline provisions credentials once; rotation is handled via operational runbooks.

### Critical distinction

**ESO sync is for runtime consumption, NOT rotation.**

ESO delivers the current active credential from Infisical to K8s so applications can consume it. It does not initiate or drive rotation. The rotation trigger is always external (Infisical scheduler, manual, or platform annotation).

### PostgreSQL single-password reality

PostgreSQL **does not natively support multiple passwords for a single role**. When `ALTER ROLE ... WITH PASSWORD 'new'` executes, the old password is **immediately invalidated**. Existing connections stay alive, but any new connection attempt (PgBouncer creating a backend connection, pod restart) using the old password fails instantly.

This means the "both passwords valid simultaneously" overlap described in earlier drafts is **not achievable with a single role**. Two patterns exist:

---

### Pattern A: Dual Role (true zero-downtime)

Follows Infisical's dual-phase rotation model:
- Reference: https://infisical.com/docs/documentation/platform/secret-rotation/overview

```
Phase 1 — Prepare
   ↓
CREATE ROLE tenant-<id>-user-v2 WITH LOGIN PASSWORD '<new-password>'
GRANT ALL PRIVILEGES ON DATABASE tenant-<id>-db TO tenant-<id>-user-v2
GRANT ALL PRIVILEGES ON ALL TABLES IN SCHEMA public TO tenant-<id>-user-v2
GRANT ALL PRIVILEGES ON ALL SEQUENCES IN SCHEMA public TO tenant-<id>-user-v2
   ↓
Both v1 and v2 roles exist and can connect simultaneously
   ↓
Update Infisical with v2 credentials  ← SOURCE OF TRUTH updated
   ↓
ESO syncs new K8s Secret to Spoke
   ↓
Pooler + PostgREST pick up v2 credential (pod restart / secret reload)
   ↓
Phase 2 — Confirm + Expire
   ↓
Confirm via metrics: 0 active connections from v1 user
   ↓
DROP ROLE tenant-<id>-user-v1
   ↓
Zero-downtime rotation complete
```

**Trade-off**: More complex. Requires tracking active role version per tenant.

---

### Pattern B: ALTER ROLE (acceptable blip)

```
ALTER ROLE tenant-<id>-user WITH PASSWORD '<new-password>'  ← old password immediately invalid
   ↓
New connections fail until ESO syncs new credential to K8s
   ↓
Update Infisical with new password
   ↓
ESO syncs new K8s Secret to Spoke (typically < 30 seconds)
   ↓
Pooler + PostgREST restart and reconnect with new password
   ↓
Rotation complete — ~10-30 second blip during scheduled window
```

**Trade-off**: Brief micro-outage during rotation. Acceptable for scheduled maintenance windows in a PaaS environment.

---

### Decision

For Phase 1 (current implementation): **Pattern B** — simpler, no role version tracking needed, blip is acceptable during a scheduled rotation window.

Pattern A can be adopted in a future phase if zero-downtime rotation becomes a hard requirement.

### Rotation trigger

Rotation is triggered externally — not by ESO:
- Infisical's built-in secret rotation scheduler
- Manual trigger via Infisical UI/API
- Platform operator annotation (e.g., `rotation.nutgraf.in/trigger`)
