# Requirements: Tenant Database Provisioning (Per-Tenant User Isolation)

**Feature Name**: `tenant-db-provisioning`
**Phase**: Phase 3 Extension — Issue #44 Fix
**Status**: Approved
**Created**: 2026-04-22
**Design Reference**: `.kiro/specs/spoke-pool-provisioner/resources/per-tenant-user-design.md`

---

## 1. Executive Summary

### 1.1 Purpose

Implement per-tenant PostgreSQL user isolation on Spoke Pool clusters. Each tenant must have a dedicated database user with isolated credentials — the shared `app` user must not be used for tenant workloads.

This is an extension to the spoke-pool-provisioner spec, specifically addressing Issue #44: the current `AINativeSaaS` Composition uses the shared `app` user for all tenants, violating security isolation.

### 1.2 Problem Statement

The current implementation uses a single shared `app` user for all tenant Poolers and PostgREST instances. A single credential compromise exposes all tenant data. The fix requires:

- A dedicated PostgreSQL user per tenant (`tenant-<id>-user`)
- Isolated credentials stored in a per-tenant Kubernetes Secret
- Durable backup of credentials in Infisical (disaster recovery)
- Clean lifecycle management (create on provision, delete on teardown)

### 1.3 Architectural Constraint

`provider-sql` cannot run on the Hub because the Spoke's CNPG (`shared-cnpg-rw`) is ClusterIP-only — not reachable cross-cluster. The solution uses the **Remote Provider Pattern**:

- Hub pushes a `TenantDatabase` XR to the Spoke via `provider-kubernetes`
- Spoke's local `provider-sql` reconciles it against its local CNPG
- No cross-cluster network path to PostgreSQL required

### 1.4 Success Criteria

- Each tenant has a dedicated PostgreSQL user with a unique 32-char random password
- User has GRANT permissions only on their own database
- Credentials stored in K8s Secret and backed up to Infisical
- Cluster rebuild recovers credentials from Infisical without breaking DB connections
- `AINativeSaaS` XR is only Ready after `TenantDatabase` is fully provisioned (DB + Role + Grants)
- AtlasMigration connects as the tenant user (not shared `app` user)

## 2. Functional Requirements

### FR-1: TenantDatabase XRD (Spoke)

**FR-1.1: TenantDatabase Custom Resource Definition**
- Define `TenantDatabase` XRD on the Spoke cluster
- Schema: `tenantId`, `databaseName`, `cellId`
- Cluster-scoped (consistent with `AINativeSaaS`)
- Composed resources: CNPG Database CR + provider-sql Role CR + Grant CRs + K8s Secret + ESO PushSecret + ESO ExternalSecret

**FR-1.2: TenantDatabase Composition (Spoke-side)**
- Composition expands `TenantDatabase` XR into all required resources locally on the Spoke
- `deletionPolicy: Delete` on all composed resources — clean cascade on XR deletion
- Sync wave ordering within Composition: ESO ExternalSecret (restore) → Secret → Role → Grants

### FR-2: Per-Tenant Database User

**FR-2.1: Dedicated PostgreSQL User**
- User naming: `tenant-<id>-user` (RFC 1123 compliant)
- Created via `provider-sql` Role CR on the Spoke
- Password: 32-character random alphanumeric generated by Crossplane `function-patch-and-transform`

**FR-2.2: Isolated Permissions**
- `GRANT CONNECT ON DATABASE tenant-<id>-db TO tenant-<id>-user`
- `GRANT ALL PRIVILEGES ON ALL TABLES IN SCHEMA public TO tenant-<id>-user`
- `GRANT ALL PRIVILEGES ON ALL SEQUENCES IN SCHEMA public TO tenant-<id>-user`
- `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON TABLES TO tenant-<id>-user`
- `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON SEQUENCES TO tenant-<id>-user`
- User has NO access to other tenant databases

**FR-2.3: Dedicated ProviderConfig (Least Privilege)**
- `crossplane_admin` role created once per Spoke Pool during cell bootstrap
- `CREATE ROLE crossplane_admin WITH LOGIN CREATEDB CREATEROLE PASSWORD '<from-infisical>'`
- `crossplane_admin` cannot read tenant data
- **Password Generation (CR Reconciliation Only):**
  - Hub Operator (SpokePool controller) watches SpokePool XRs on Hub
  - On CR reconciliation, controller checks status condition: first-time creation?
  - **Infisical Key Naming:** Password key MUST be derived from SpokePool CR name: `<spokepool-cr-name>-crossplane-admin-password`
    - Example: SpokePool CR `spoke-pool-eu-prod-01` → Infisical key `spoke-pool-eu-prod-01-crossplane-admin-password`
    - This ensures each SpokePool has a unique, identifiable password in Infisical
  - Controller queries Infisical API for existing password using the derived key (idempotency check)
  - If password exists in Infisical → skip generation (idempotent)
  - If password missing AND first-time creation → generate 32-char hex password using `secrets.GenerateSecurePassword()` and upload to Infisical at `/spoke-pool/<spokepool-cr-name>-crossplane-admin-password`
  - If password missing AND NOT first-time → FAIL reconciliation with error (requires manual intervention)
  - **Operator does NOT create Hub K8s secret**
  - **Operator does NOT manage secret lifecycle post-creation**
- ESO syncs from Infisical to `crossplane-admin-credentials` Secret in `spoke-platform-ops` namespace

### FR-3: Credential Secret

**FR-3.1: K8s Secret Generation**
- Secret name: `tenant-<id>-db-credentials`
- Namespace: `tenant-<id>`
- Fields: `username`, `password`, `database`, `host`, `port`
- Generated by Crossplane on the Spoke — not pulled from Infisical on first creation

**FR-3.2: Infisical Backup (Mandatory)**
- ESO `PushSecret` mirrors Secret to Infisical immediately after creation
- Infisical path: `/spoke-pool/<cell-id>/tenants/<tenant-id>/db-credentials`
- Required for disaster recovery — without this, cluster rebuild generates a new password that doesn't match the DB

**FR-3.3: Disaster Recovery Pull**
- ESO `ExternalSecret` with `creationPolicy: Merge` pulls from Infisical on cluster rebuild
- Restores existing password before Crossplane reconciles the Role
- Prevents Crossplane from generating a new mismatched password

### FR-4: Hub Composition Update

**FR-4.1: AINativeSaaS Composition — TenantDatabase Object**
- Replace direct `db-user`, `grant-*`, `db-credentials-secret` resources in Hub Composition
- Add single `provider-kubernetes Object` wrapping `TenantDatabase` CR pushed to Spoke
- `readinessChecks: MatchCondition Ready=True` — Hub Object only Ready when Spoke's `TenantDatabase` is fully reconciled

**FR-4.2: Pooler uses tenant credentials**
- CNPG Pooler `authQueryUser.secretRef` references `tenant-<id>-db-credentials`
- Shared `app` user removed from Pooler configuration

**FR-4.3: PostgREST uses tenant credentials**
- `PGRST_DB_URI` sourced from `tenant-<id>-db-credentials` Secret
- `PGRST_DB_ANON_ROLE` set to `tenant-<id>-user`
- Shared `app` user removed from PostgREST configuration

### FR-5: provider-sql on Spoke

**FR-5.1: provider-sql deployment**
- `provider-sql` v0.9.0 installed on every Spoke Pool via edge catalog
- Sync wave 0 (before CNPG operator)
- `ProviderConfig` points to `shared-cnpg-rw.spoke-platform-data.svc.cluster.local:5432`
- Uses `crossplane-admin-credentials` Secret

**FR-5.2: Remove provider-sql from Hub**
- `provider-sql` removed from `manifests/hub-core-services/crossplane/providers/`
- Hub only uses `provider-kubernetes` for cross-cluster resource management

## 3. Non-Functional Requirements

### NFR-1: Security
- **NFR-1.1**: Shared `app` user MUST NOT be used for any tenant Pooler or PostgREST connection
- **NFR-1.2**: Each tenant user has GRANT permissions only on their own database — cross-tenant access impossible
- **NFR-1.3**: `crossplane_admin` has no read access to tenant data
- **NFR-1.4**: All credentials stored in Infisical (audit trail, access control)

### NFR-2: Reliability
- **NFR-2.1**: Cluster rebuild must not break tenant DB connections — credentials recovered from Infisical
- **NFR-2.2**: `provider-sql` drift detection continuously reconciles Role/Grant state
- **NFR-2.3**: If role is manually dropped, `provider-sql` re-creates it automatically

### NFR-3: Scalability
- **NFR-3.1**: Each `TenantDatabase` XR is independent — no shared mutable arrays
- **NFR-3.2**: 50+ concurrent tenant provisioning must not cause race conditions or etcd contention
- **NFR-3.3**: `provider-sql` reconciliation rate tunable via `--max-reconcile-rate` if needed

### NFR-4: Sync Wave Ordering
- **NFR-4.1**: `AINativeSaaS` XR (Wave 1) must be Ready before `AtlasMigration` (Wave 2) starts
- **NFR-4.2**: `readinessChecks` on Hub's provider-kubernetes Object gates Wave 2 correctly
- **NFR-4.3**: Within TenantDatabase Composition: ESO restore → Secret → Role → Grants (ordered)

## 4. Acceptance Criteria

| ID | Criteria |
|----|----------|
| AC-1 | `TenantDatabase` XRD and Composition exist on Spoke cluster |
| AC-2 | Applying `TenantDatabase` XR creates: CNPG Database + Role + Grants + Secret |
| AC-3 | `tenant-<id>-user` can connect to `tenant-<id>-db` |
| AC-4 | `tenant-<id>-user` CANNOT connect to any other tenant database |
| AC-5 | `tenant-<id>-db-credentials` Secret exists in `tenant-<id>` namespace |
| AC-6 | Secret is mirrored to Infisical via PushSecret |
| AC-7 | Cluster rebuild restores Secret from Infisical — DB connections recover without manual intervention |
| AC-8 | `AINativeSaaS` XR is only Ready after `TenantDatabase` Ready=True |
| AC-9 | AtlasMigration connects as `tenant-<id>-user` (not `app` user) |
| AC-10 | Pooler logs show `tenant-<id>-user` — no `app` user references |
| AC-11 | PostgREST logs show `tenant-<id>-user` — no `app` user references |
| AC-12 | Deleting `AINativeSaaS` XR cleans up Role, Grants, Database, and Secret |
