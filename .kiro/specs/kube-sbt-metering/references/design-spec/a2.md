## Report: Spoke Data Collection Architecture

**NO, spoke data is NOT collected using an OTel Collector DaemonSet.**

### Actual Architecture:

1. **OTel Collector Deployment Type**: **Deployment** (not DaemonSet)
   - Location: `manifests/spoke-pool/otel-collector/deployment.yaml`
   - Replicas: 3 (HA configuration)
   - Single cluster-level collector per spoke cluster

2. **MetricCollector Deployment Type**: **Sidecar Container** (not DaemonSet)
   - Runs as sidecar in PostgREST pods
   - One sidecar per tenant's PostgREST deployment
   - Continuously queries tenant database for domain metrics

3. **Data Flow**:
   - AgentGateway → emits OTLP directly to Hub OpenMeter (hot path)
   - MetricCollector (sidecar) → local OTel Collector (spoke) → Hub OpenMeter
   - Pattern: Agent → Gateway → Backend (centralized aggregation)

4. **Key Design Decision** (from Section 10.6):
   - Rejected: Per-tenant CronJobs (doesn't scale to 1000+ tenants)
   - Chosen: Single cluster-level OTel Collector **Deployment** + per-tenant metric collector **sidecars**
   - Rationale: ADR-011 compliance (declarative operator state over imperative jobs)

The architecture uses **Deployment** (centralized, cluster-level) rather than **DaemonSet** (per-node) because the collection pattern is tenant-aware aggregation, not node-level metrics.

### Grafana Alloy + VictoriaMetrics is a legitimate replacement for the OTel DaemonSet Agent

**Grafana Alloy** is a fully capable OpenTelemetry-compatible collector that can run as a DaemonSet and collect node-level metrics natively. It's not just a pipeline tool — it replaces both the Prometheus Node Exporter scraping layer and the OTel agent tier.

### What Alloy covers in spoke clusters

| Capability | Alloy (DaemonSet) |
|---|---|
| Node/kubelet metrics | ✅ via `prometheus.scrape` + `discovery.kubernetes` |
| Pod/container metrics | ✅ |
| OTLP emit to Hub | ✅ native |
| Log collection | ✅ |
| Replaces Node Exporter | ✅ |

### How this fits your design

```
Spoke Cluster
├── DaemonSet: Grafana Alloy       ← node/infra metrics (fills the gap)
├── Deployment: OTel Gateway (HA)  ← your existing tenant aggregation
├── Sidecar: MetricCollector       ← tenant DB metrics
└── → Hub VictoriaMetrics
```

Alloy on a DaemonSet feeds the spoke OTel Gateway, which forwards to Hub VictoriaMetrics. The hot path (AgentGateway → Hub OpenMeter) stays unchanged. **This is a solid, enterprise-grade stack.**

### One thing to verify

If the design doc has Alloy running as a **Deployment** (not DaemonSet) in spokes, you're back to the gateway-only pattern — Alloy in that mode won't collect per-node metrics. Check whether it's `kind: DaemonSet` in the manifests. If it is, you're covered and the agent-tier gap I flagged earlier is already solved.

### VictoriaMetrics fit

It's a strong choice as the Hub backend — better cardinality handling than Prometheus at scale, and Headlamp can point its Prometheus plugin at it directly, giving you the UI layer too. The full stack then becomes:

```
Alloy (DaemonSet, spoke) → OTel Gateway (spoke) → VictoriaMetrics (hub) ← Headlamp UI
```

That's a coherent, well-integrated observability architecture with no major gaps.
