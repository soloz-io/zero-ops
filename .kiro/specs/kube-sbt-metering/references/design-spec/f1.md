# GAP Analysis: Waypoint Builder Design Spec

After a rigorous review of the provided Waypoint Builder design specifications against the actual Vercel Workflow SDK (WDK) codebase and architecture, several critical technical gaps, logical inconsistencies, and edge cases have been identified. 

The WDK is a highly opinionated, deterministic VM-based execution engine. Deviations from its expected bundling and execution patterns will result in runtime failures. 

Here is the gap analysis categorized by domain, followed by actionable questions for the product team.

---

## 1. WDK Runtime & Compilation Gaps (CRITICAL)

**1.1. VM Sandbox Restrictions on Imports (`kagentEvaluate`)**
*   **The Gap**: The custom CodeGen design (`generateWorkflowCode`) injects raw imports like `import { kagentEvaluate } from './kagent-client';` directly into the workflow function.
*   **The Reality**: WDK's `workflowEntrypoint` executes code inside a strict `node:vm` sandbox (`packages/core/src/vm/index.ts`). It explicitly lacks access to the host's module resolution (`require` and dynamic `import` are stubbed). Furthermore, standard API primitives like `fetch` are stubbed out to prevent non-deterministic side effects.
*   **The Fix**: `kagentEvaluate` **must** be implemented as a Step function (`"use step"`), bundled by the control plane, and invoked inside the workflow via the WDK step resolution system (`globalThis[Symbol.for('WORKFLOW_USE_STEP')]('kagentEvaluate')`).

**1.2. The Missing Esbuild/SWC Bundling Phase**
*   **The Gap**: The design implies taking the raw string output from `generateWorkflowCode()` and saving it to the DB/Git for execution.
*   **The Reality**: WDK workflows *must* go through the `@workflow/builders` (esbuild + SWC plugin) compilation phase. This phase extracts step functions, sets `stepId`s, hoists closure variables, and replaces `import { step }` with internal symbol lookups. Raw TS strings cannot be safely executed by `workflowEntrypoint(code)`.
*   **The Fix**: The Control Plane API must invoke `@workflow/builders` programmatically to produce the intermediate `cjs` bundle required by the VM before saving it to the database/Git.

**1.3. Infinite Loop Risk in State Machine Pattern**
*   **The Gap**: In the generated code example, if `transitionType === 'agentic'`, the code awaits `kagentEvaluate`. If it evaluates to `false`, it breaks out of the `switch` statement, loops back to the `while(!isComplete)`, and immediately re-evaluates the agentic step.
*   **The Reality**: This creates a tight infinite loop. The WDK will rapidly exhaust its `MAX_QUEUE_DELIVERIES` or hit the `REPLAY_TIMEOUT_MS` (240s) limits, failing the run.
*   **The Fix**: If a state's transitions are not met, the workflow *must* suspend (either via a `sleep()` delay before re-evaluating, or waiting on a `createHook()`).

## 2. Event Sourcing & Real-Time Notifications

**2.1. Incorrect Usage of `workflow_event_chunk` LISTEN/NOTIFY**
*   **The Gap**: Requirement 8 states the Control Plane will subscribe to PostgreSQL's `workflow_event_chunk` channel to see state changes in real time.
*   **The Reality**: In `@workflow/world-postgres`, the `workflow_event_chunk` channel is *only* triggered when user code explicitly calls `getWritable().write()` (user data streams). It does **not** broadcast internal state machine lifecycle events like `run_started`, `step_completed`, or `hook_created`.
*   **The Fix**: To achieve real-time state updates, you must add custom PostgreSQL Triggers on the `workflow_events` and `workflow_hooks` tables that broadcast to a new channel (e.g., `blueprint_state_changes`).

**2.2. Webhook Token Security & Exposure**
*   **The Gap**: The Spoke UI queries `GET /workflow_hooks?run_id=eq.order_123` to render transition buttons based on the `token` field.
*   **The Reality**: Webhook tokens in WDK are meant to be secure secrets. If the Spoke UI fetches raw tokens to construct `resumeHook()` calls, any user with read access to the UI could theoretically capture tokens and force transitions they shouldn't.
*   **The Fix**: Transition tokens must be securely managed. RBAC (`allowed_roles`) must be embedded in the `hook.metadata` during `createHook({ metadata: { allowed_roles: [...] } })`, and the `/api/webhooks/resume` endpoint must validate the user's role against the hook's metadata *before* calling `resumeHook`.

## 3. Architecture & Data Flow Inconsistencies

**3.1. Disconnect between GitOps and Database Execution**
*   **The Gap**: Requirement 10 states ArgoCD syncs the compiled code to `tenants/{tenantId}/blueprints/{name}.ts`. However, Section 5.1 (`server.ts`) queries the database (`SELECT compiled_code FROM workflow_runs WHERE id = $1`) to execute the workflow.
*   **The Reality**: The Spoke Worker needs to know *where* to get the code. If the code is fetched from the DB, GitOps is bypassed at runtime. If the code is in Git (and mounted to the pod via ConfigMap/Volume), reading from the DB is obsolete.
*   **The Fix**: Clarify the source of truth for runtime code. If using GitOps, the Spoke Worker should import the files directly from the filesystem (mounted by Kubernetes) rather than querying `compiled_code` from Postgres.

**3.2. Dynamic Form Fields `{{record.salary}}` Context Resolution**
*   **The Gap**: Requirement 11 allows workflows to evaluate conditions like `{{record.salary}} > 100000`. The generated code passes `recordId` into the workflow. 
*   **The Reality**: The workflow VM does not magically have access to the tenant's database to resolve `record.salary`.
*   **The Fix**: The workflow must start by executing a predefined Step (`fetchRecordDataStep`) to pull the record data into memory before entering the state machine loop, or the Control Plane must fetch the record and pass it directly into the workflow via `triggerInput`.

**3.3. Parallel Transition Race Conditions**
*   **The Gap**: Requirement 15 mandates "Parallel Transition Execution" (Promise.all).
*   **The Reality**: In a State Machine, executing multiple outbound transitions in parallel introduces race conditions. If State A has Transition B (Agentic) and Transition C (Agentic) executing via `Promise.all()`, and *both* evaluate to true simultaneously, which target state does the machine move to? 
*   **The Fix**: State machine evaluation must be sequential (e.g., evaluating conditions in priority order) OR the spec must define deterministic resolution logic for competing parallel transitions.

## Actionable Questions for the Product & Engineering Teams

To mark this spec as "Development Ready", please address the following:

1. **Sandbox Execution:** The WDK heavily restricts execution inside the VM. Do you want the Control Plane to run the full `@workflow/builders` compilation (esbuild/SWC) before saving to the DB, or should the Spoke Worker compile the raw TS string on the fly? *(Recommendation: Control plane pre-compiles using the Builder API).*
2. **Infinite Loops in State Machines:** If an agentic transition is rejected, and no human transition exists for that state, how should the workflow behave? Should it sleep for X hours before asking the agent again, or move to a "Stuck/Failed" state?
3. **Data Hydration:** Instead of passing just `recordId` into the workflow, can we pass the entire `Record` object at workflow start? This prevents us from having to write a database-query Step function just to evaluate `{{record.amount}} > 100`.
4. **GitOps vs Database:** The design writes code to Git (ArgoCD) but executes code from PostgreSQL (`SELECT compiled_code FROM workflow_runs`). Which one is the actual source of truth for the Spoke worker?
5. **Real-time Engine:** WDK doesn't broadcast state changes over Postgres `LISTEN/NOTIFY` out-of-the-box. Are we comfortable adding custom PostgreSQL triggers to the WDK schema to support the UI's real-time requirements?
6. **Parallelism:** If two parallel intent evaluations (e.g., "Is High Value?" and "Requires Manual Review?") both resolve to true, which state does the workflow transition to?

-------------------

Based on my investigation of the Vercel Workflow SDK codebase, I can now provide answers to the 6 critical questions in the gap analysis:

## Answers to Actionable Questions

### 1. **Sandbox Execution & Compilation**
**Answer**: Control Plane MUST pre-compile using `@workflow/builders` API.

**Reality**: The WDK requires a complete esbuild + SWC transformation pipeline. The SWC plugin (`@workflow/swc-plugin`) extracts functions with `"use step"` directives, generates unique `stepId`s (format: `step//path/to/file.ts//functionName`), and transforms them into symbol-based lookups. Raw TypeScript strings cannot be executed by `workflowEntrypoint`.

**Implementation**: 
- Control Plane must invoke `applySwcTransform()` from `@workflow/builders` 
- This produces a CJS bundle with step functions properly registered
- The compiled bundle (not raw TS) gets stored in DB/Git
- `kagentEvaluate` must be a separate step function file, not an import

### 2. **Infinite Loops in State Machines**
**Answer**: Workflow MUST suspend via `createHook()` or `sleep()` when no transition is eligible.

**Reality**: The generated while/switch pattern will create tight loops if agentic evaluation returns false and no other transition exists. WDK will hit `MAX_QUEUE_DELIVERIES` (10) or `REPLAY_TIMEOUT_MS` (240s) limits.

**Recommendation**: 
- If all agentic transitions reject: create a fallback `createHook()` for human intervention
- OR: inject `await sleep('1h')` before re-evaluating agentic transitions
- OR: move to a "Stuck" state that requires manual resolution

### 3. **Data Hydration**
**Answer**: Pass entire `Record` object at workflow start via `triggerInput`.

**Reality**: The VM sandbox has no database access. Passing only `recordId` requires writing a `fetchRecordDataStep` function, which adds complexity and latency.

**Recommendation**:
- Control Plane fetches record data before calling `start(workflow, [recordData])`
- Workflow receives full record object: `export async function blueprint(record: Record, initialState: string)`
- Field references like `{{record.salary}}` compile to direct property access: `record.salary`

### 4. **GitOps vs Database**
**Answer**: Database is source of truth for runtime execution. GitOps is for infrastructure only.

**Reality**: The design has a logical inconsistency. ArgoCD syncs K8s manifests (Deployments, Services, Secrets), NOT application code. The compiled workflow code must be stored in PostgreSQL and fetched at runtime.

**Clarification**:
- GitOps (ArgoCD): Manages K8s resources (namespaces, deployments, network policies)
- Database: Stores compiled workflow code in `workflow_runs.compiled_code` or separate `blueprint_deployments` table
- Spoke Worker queries DB to load code: `SELECT compiled_code FROM workflow_runs WHERE id = $1`
- Remove the Git commit step for compiled code from deployment flow

### 5. **Real-time Engine**
**Answer**: Yes, add custom PostgreSQL triggers to broadcast state changes.

**Reality**: `workflow_event_chunk` channel only fires for user-initiated `getWritable().write()` calls, NOT for internal lifecycle events (`step_completed`, `hook_created`, etc.).

**Implementation**:
```sql
-- Add trigger to workflow_events table
CREATE OR REPLACE FUNCTION notify_blueprint_state_change()
RETURNS TRIGGER AS $$
BEGIN
  PERFORM pg_notify('blueprint_state_changes', 
    json_build_object(
      'run_id', NEW.run_id,
      'event_type', NEW.event_type,
      'correlation_id', NEW.correlation_id
    )::text
  );
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER blueprint_state_change_trigger
AFTER INSERT ON workflow_events
FOR EACH ROW
EXECUTE FUNCTION notify_blueprint_state_change();

-- Add trigger to workflow_hooks table
CREATE TRIGGER blueprint_hook_created_trigger
AFTER INSERT ON workflow_hooks
FOR EACH ROW
EXECUTE FUNCTION notify_blueprint_state_change();
```

Control Plane subscribes to `blueprint_state_changes` channel instead of `workflow_event_chunk`.

### 6. **Parallelism**
**Answer**: Sequential evaluation with priority order. No true parallelism for competing transitions.

**Reality**: State machines are deterministic by definition. If two transitions from the same state both evaluate to true, the system must have a deterministic resolution strategy.

**Recommendation**:
- **Option A (Sequential)**: Evaluate transitions in canvas order (top-to-bottom). First transition that evaluates to true wins.
- **Option B (Priority)**: Add explicit `priority` field to transition nodes. Highest priority wins.
- **Option C (Split State)**: If truly parallel, the state should split into multiple concurrent states (advanced state machine pattern, not in V1 scope)

**Requirement 15 Update**: Change "Parallel Transition Execution" to "Parallel Action Execution within a Single Transition" - meaning one transition can have multiple independent actions (email + Slack + Jira) that run via `Promise.all()`, but transition selection itself remains sequential.

## Critical Design Updates Needed

1. **Section 4.2 (Compiler)**: Add `@workflow/builders` invocation before saving code
2. **Section 4.2 (Compiler)**: Change `kagentEvaluate` from import to separate step function file
3. **Section 4.2 (Compiler)**: Add fallback suspension logic when no transitions are eligible
4. **Section 3.1 (Data Models)**: Remove `compiled_code` from `workflow_runs`, keep only in `blueprint_deployments`
5. **Section 5.3 (LISTEN/NOTIFY)**: Replace `workflow_event_chunk` with custom `blueprint_state_changes` trigger
6. **Section 6.2 (Deployment)**: Remove Git commit for compiled code, keep only for K8s manifests
7. **Requirement 15**: Clarify parallelism is for actions within a transition, not competing transitions
