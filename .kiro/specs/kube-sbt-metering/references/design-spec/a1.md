Here are the definitive **Yes/No** answers to your implementation questions. These decisions align tightly with the `sbt-aws` philosophy, the existing `zero-ops` codebase patterns, and the zero-trust Hub-Spoke architecture.

---

### **Domain 1: Hub-Spoke Architecture & Deployment**

**Q1.1: Should kube-sbt be deployed as a single monolithic API server binary?**
**Yes (Single Binary).** `kube-sbt` (existing as `cmd/opensbt`) should remain a unified Control Plane API server binary. This avoids unnecessary microservice sprawl in the Hub while maintaining logical separation internally via interfaces.

**Q1.2: Should kube-sbt use Gin framework for REST API implementation?**
**Yes.** Use Gin. It aligns perfectly with the existing `opensbt` and `zero-ops-api` implementations in the codebase.

**Q1.3: Should kube-sbt be deployed via Helm chart managed by ArgoCD?**
**Yes.** It must be deployed via ArgoCD referencing a Helm chart/kustomize overlay (e.g., in `manifests/hub-core-services/opensbt/`), adhering to the strict GitOps-first deployment model.

---

### **Domain 2: OpenMeter Integration Architecture**

**Q2.1: Should kube-sbt use OpenMeter's official Go SDK client?**
**Yes.** Use the official OpenMeter Go SDK. This guarantees type safety, automatic schema alignment, and built-in retry mechanisms over manual HTTP calls.

**Q2.2: Is OpenMeter namespace provisioning handled exclusively by Crossplane?**
**Yes (Exclusively Crossplane).** `kube-sbt` must assume the namespace is already created (Req 19.6). The `AINativeSaaS` XR composition in Crossplane will use `provider-http` to initialize the namespace during tenant creation.

**Q2.3: Should the `OpenMeter-Namespace` header value come from JWT claims (`tenant_id`)?**
**Yes (From JWT Claims).** To enforce zero-trust security and prevent tenant spoofing via path manipulation, the `OpenMeter-Namespace` header MUST be populated strictly from the validated Ory JWT `tenant_id` claim.

---

### **Domain 3: User Management & Subject Registration**

**Q3.1: Should user creation go through Ory Kratos first, then register in OpenMeter?**
**Yes (Kratos First).** Ory Kratos is the Identity Source of Truth. The flow is: Create in Kratos → Create Subject in OpenMeter → Fallback/Rollback if OpenMeter fails.

**Q3.2: Should `GenerateSubjectID()` use UUIDs (`tenant_id#user_id`)?**
**Yes.** Use the `{tenant_id}#{user_id}` string format exactly. This avoids exposing PII (like emails) in telemetry pipelines and guarantees global uniqueness in OpenMeter.

**Q3.3: Should orphaned subject reconciliation run as a background goroutine within the kube-sbt process?**
**Yes.** Run it as a managed background worker (goroutine) within the `kube-sbt` process, listening to the NATS JetStream `opensbt_orphanedSubjects` topic. This avoids the complexity of deploying and monitoring a separate Kubernetes CronJob.

---

### **Domain 4: Database & Migrations**

**Q4.1: Does the `public.users` table migration target Spoke cluster tenant databases?**
**Yes (Spoke Clusters).** The `public.users` table holds tenant application data. It must be provisioned via Atlas migrations applied to the Spoke tenant databases during GitOps provisioning (e.g., `migrations/tenant-baseline/`).

**Q4.2: Should kube-sbt use `sqlc` for database access?**
**Yes.** Maintain consistency with the existing codebase by using `sqlc` for type-safe SQL queries against the Hub database (e.g., for the `processed_events` table used in Stripe webhook idempotency).

**Q4.3: Should kube-sbt ever make direct SQL connections to Spoke cluster tenant databases?**
**No (Never).** Cross-cluster direct SQL connections violate isolation boundaries. `kube-sbt` must only communicate with Spokes via asynchronous events (NATS) or REST APIs (PostgREST).

---

### **Domain 5: mTLS & Zero-Trust Security**

**Q5.1: Should kube-sbt Go code make plain HTTP calls (Envoy handles mTLS)?**
**Yes.** The Go code uses standard HTTP clients (`http://openmeter...`). The Istio Envoy sidecar transparently intercepts outbound traffic, provisions the SPIFFE SVID, and upgrades the connection to mTLS.

**Q5.2: Should kube-sbt Go code validate SPIFFE SVIDs from incoming requests?**
**No.** Istio's `PeerAuthentication` (STRICT mode) and `AuthorizationPolicy` handle all cryptographic validation and principal enforcement. The Go application trusts the mesh.

---

### **Domain 6: NATS Event Choreography**

**Q6.1: Should kube-sbt use the existing NATS provider in `internal/opensbt/providers/nats/`?**
**Yes.** Extend the existing `IEventBus` implementation to support the new billing, metering, and DLQ events.

**Q6.2: Should NATS event topics use the `opensbt_` prefix?**
**Yes.** Continue using the `opensbt_{eventType}` naming convention (e.g., `opensbt_orphanedSubjects`, `opensbt_billingSuccess`) to match existing `models/events.go` patterns.

---

### **Domain 7: Stripe Integration**

**Q7.1: Should kube-sbt create Stripe subscriptions directly via Stripe SDK?**
**No (Delegate to OpenMeter).** `kube-sbt` must strictly use OpenMeter APIs. OpenMeter's native Stripe App handles pushing the subscriptions, pricing, and prorations to Stripe.

**Q7.2: Should Stripe webhook secrets be injected as environment variables?**
**Yes.** Inject them as environment variables via the External Secrets Operator (ESO). ESO fetches the secret from Infisical and mounts it securely into the deployment's `envFrom`.

---

### **Domain 8: Testing & Validation**

**Q8.1: Should manual validation use the existing "app-creator" tenant from fleet-registry?**
**Yes.** Use the existing "app-creator" tenant to validate against a real-world GitOps footprint and avoid test-environment drift.

**Q8.2: Should E2E tests use Testcontainers-Go for real dependencies?**
**Yes.** E2E tests must use `Testcontainers-Go` for PostgreSQL, NATS, and OpenMeter to ensure high fidelity, matching the pattern established in `internal/api/handlers/e2e/testcontainer.go`.

---

### **Domain 9: Code Organization**

**Q9.1: Should OpenMeter integration code live in `internal/opensbt/providers/openmeter/`?**
**Yes.** Create a new package `internal/opensbt/providers/openmeter/` containing `metering.go` and `billing.go` implementing the `IMetering` and `IBilling` interfaces.

**Q9.2: Should the legacy Postgres-backed metering implementation be deleted entirely?**
**Yes.** Completely delete `internal/opensbt/providers/metering/` and its associated SQL migrations (`004_metering.sql`). Keeping dead code creates technical debt and split-brain logic.

---

### **Domain 10: OpenAPI & Documentation**

**Q10.1: Should the OpenAPI spec be manually written, or auto-generated from Go code annotations?**
**No (Auto-generate).** Use code annotations (e.g., `swaggo/swag`) to auto-generate the OpenAPI 3.0 specification. This ensures the Go code and the API documentation never drift.

**Q10.2: Should OpenAPI examples use real JWT tokens from Ory Hydra?**
**No (Use placeholders).** Static documentation must use placeholders like `<YOUR_JWT_TOKEN>`. Pair the docs with a utility script (e.g., `scripts/get-token.sh`) or Postman pre-request scripts to fetch real, unexpired tokens during active testing.
