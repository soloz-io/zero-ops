# 2026-09-02 — observations

Both entries below come from one investigation: an EphemeralJob that pended
forever on the dev spoke. Neither is the bug that was being looked for.

## 1. ArgoCD reports successful syncs while applying nothing

`infrastructure-provider` was synced to current `HEAD`, its last operation said
`successfully synced (all tasks run)`, and each resource in the sync result said
`serverside-applied`. The ClusterClass it manages was five days stale.

The cause is upstream of ArgoCD's own logic. The application-controller could not
resolve the repo-server:

```
dial tcp: lookup argocd-repo-server on 10.96.0.10:53: no such host
dial tcp: lookup argocd-repo-server: i/o timeout
```

Manifest generation lives in repo-server, so with it unreachable the controller
has no target state. It cannot diff, and automated sync cannot run because
auto-sync requires a successful comparison. What it *did* run were partial syncs
over a stale cached manifest set — three resources rather than the app's
nineteen — and each of those reported success, because the apply genuinely
succeeded. It applied the old content.

The only true signal was a `ComparisonError` condition in
`status.conditions`, which no dashboard surfaces and which disappears the moment
DNS recovers, leaving the stale cluster behind and nothing to show why.

Two things made this expensive. The first is that every summary field agreed the
app was fine: `Synced` revision current, operation `Succeeded`, health `Healthy`
on most resources. The second is that the failure is intermittent, so a check run
during a good minute shows a clean comparison and a check run a minute later
shows an error, and neither reflects what was actually applied five days ago.

The field that did not lie was `managedFields`. `argocd-controller`'s ownership
entry for `spec.workers` was timestamped 2026-08-27 while the app claimed to be
synced to a commit from 2026-09-02. Server-side apply records when a manager last
wrote a field, so ownership timestamps answer "did ArgoCD actually write this?"
directly, and they answer it for an object whose diff is currently uncomputable.

The blast radius was not one Application. At the time `api-gateway`, `auth-proxy`,
`grafana-alloy`, `ingress-config`, `kratos-selfservice-ui` and `mcp-server` were
all OutOfSync or Progressing against the same cause. Anything merged in the
preceding five days should be assumed unapplied until checked.

What is missing is an alert on `ComparisonError`. It is a condition on the
Application, it is unambiguous — the controller is saying it cannot determine
desired state — and it is the one signal that was present throughout. Without it
the failure is only visible by noticing that a specific field did not change,
which requires already suspecting the specific field.

Worth pairing with a staleness check: an Application whose `status.sync.revision`
advances while its managed objects' `managedFields` timestamps do not is applying
nothing, whatever it reports.

## 2. Cluster DNS on the hub fails intermittently for in-cluster names

The resolution failure above is not specific to ArgoCD. Both CoreDNS replicas on
the hub are also failing to reach upstream resolvers:

```
[ERROR] plugin/errors: 2 github.com. A: read udp 10.244.0.69:53153->1.0.0.1:53: i/o timeout
```

and queries for cluster-internal names are falling through to the node's tailnet
search domain, which forwards off-cluster and then times out:

```
ory-hydra-public.platform-identity.svc.cluster.local.taila4c44b.ts.net. A: i/o timeout
infisical-standalone-infisical.platform-security.svc.taila4c44b.ts.net. AAAA: i/o timeout
```

A name reaching the `.taila4c44b.ts.net` suffix means the cluster-internal lookup
already returned NXDOMAIN — the resolver only appends the next search domain when
the previous one fails. So the fallthrough is a symptom of internal resolution
failing, and it then adds load to an upstream path that is itself failing.

The hub is hybrid: one CoreDNS replica runs on a Hetzner control-plane node and
one on a home Flatcar node, with pod-to-pod traffic crossing Tailscale. The
home-node replica logged `waiting for Kubernetes API before starting server` and
`Still waiting on: kubernetes` at startup, so its ability to watch Services is
the thing to examine first — a replica that cannot watch Services answers
NXDOMAIN for every Service name, which produces exactly this alternation between
`no such host` and `i/o timeout` as queries land on one replica or the other.

Resolver configuration on the affected pods is correct and is not the cause:
`platform-ops.svc.cluster.local` is first in the search list, `ndots:5`, with the
tailnet domain last. The resolution succeeded 10/10 when retested later, which is
what makes this intermittent rather than broken, and what makes it survive
casual checking.

This is the same fault the CoreDNS investigation is already tracking. Recording
it here because its consequence is now known to be larger than slow lookups: it
silently stops GitOps from applying anything, across every Application on the
hub, while every status field continues to read healthy.
