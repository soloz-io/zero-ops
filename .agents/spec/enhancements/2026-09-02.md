# 2026-09-02 — observations

All four entries below come from one investigation: an EphemeralJob that pended
forever on the dev spoke. None of them is the bug that was being looked for, and
three of the four are cases of a component reporting success while doing nothing.

## 1. ArgoCD reports successful syncs while applying nothing

`infrastructure-provider` was synced to current `HEAD`, its last operation said
`successfully synced (all tasks run)`, and each resource in the sync result said
`serverside-applied`. The ClusterClass it manages was five days stale.

The cause is upstream of ArgoCD's own logic. The application-controller could not
resolve the repo-server:

```
dial tcp: lookup argocd-repo-server on 10.96.0.10:53: no such host
dial tcp: lookup argocd-repo-server: i/o timeout
```

Manifest generation lives in repo-server, so with it unreachable the controller
has no target state. It cannot diff, and automated sync cannot run because
auto-sync requires a successful comparison. What it *did* run were partial syncs
over a stale cached manifest set — three resources rather than the app's
nineteen — and each of those reported success, because the apply genuinely
succeeded. It applied the old content.

The only true signal was a `ComparisonError` condition in
`status.conditions`, which no dashboard surfaces and which disappears the moment
DNS recovers, leaving the stale cluster behind and nothing to show why.

Two things made this expensive. The first is that every summary field agreed the
app was fine: `Synced` revision current, operation `Succeeded`, health `Healthy`
on most resources. The second is that the failure is intermittent, so a check run
during a good minute shows a clean comparison and a check run a minute later
shows an error, and neither reflects what was actually applied five days ago.

The field that did not lie was `managedFields`. `argocd-controller`'s ownership
entry for `spec.workers` was timestamped 2026-08-27 while the app claimed to be
synced to a commit from 2026-09-02. Server-side apply records when a manager last
wrote a field, so ownership timestamps answer "did ArgoCD actually write this?"
directly, and they answer it for an object whose diff is currently uncomputable.

The blast radius was not one Application. At the time `api-gateway`, `auth-proxy`,
`grafana-alloy`, `ingress-config`, `kratos-selfservice-ui` and `mcp-server` were
all OutOfSync or Progressing against the same cause. Anything merged in the
preceding five days should be assumed unapplied until checked.

What is missing is an alert on `ComparisonError`. It is a condition on the
Application, it is unambiguous — the controller is saying it cannot determine
desired state — and it is the one signal that was present throughout. Without it
the failure is only visible by noticing that a specific field did not change,
which requires already suspecting the specific field.

Worth pairing with a staleness check: an Application whose `status.sync.revision`
advances while its managed objects' `managedFields` timestamps do not is applying
nothing, whatever it reports.

## 2. Cluster DNS on the hub fails intermittently for in-cluster names

The resolution failure above is not specific to ArgoCD. Both CoreDNS replicas on
the hub are also failing to reach upstream resolvers:

```
[ERROR] plugin/errors: 2 github.com. A: read udp 10.244.0.69:53153->1.0.0.1:53: i/o timeout
```

and queries for cluster-internal names are falling through to the node's tailnet
search domain, which forwards off-cluster and then times out:

```
ory-hydra-public.platform-identity.svc.cluster.local.taila4c44b.ts.net. A: i/o timeout
infisical-standalone-infisical.platform-security.svc.taila4c44b.ts.net. AAAA: i/o timeout
```

A name reaching the `.taila4c44b.ts.net` suffix means the cluster-internal lookup
already returned NXDOMAIN — the resolver only appends the next search domain when
the previous one fails. So the fallthrough is a symptom of internal resolution
failing, and it then adds load to an upstream path that is itself failing.

The hub is hybrid: one CoreDNS replica runs on a Hetzner control-plane node and
one on a home Flatcar node, with pod-to-pod traffic crossing Tailscale. The
home-node replica logged `waiting for Kubernetes API before starting server` and
`Still waiting on: kubernetes` at startup, so its ability to watch Services is
the thing to examine first — a replica that cannot watch Services answers
NXDOMAIN for every Service name, which produces exactly this alternation between
`no such host` and `i/o timeout` as queries land on one replica or the other.

Resolver configuration on the affected pods is correct and is not the cause:
`platform-ops.svc.cluster.local` is first in the search list, `ndots:5`, with the
tailnet domain last. The resolution succeeded 10/10 when retested later, which is
what makes this intermittent rather than broken, and what makes it survive
casual checking.

This is the same fault the CoreDNS investigation is already tracking. Recording
it here because its consequence is now known to be larger than slow lookups: it
silently stops GitOps from applying anything, across every Application on the
hub, while every status field continues to read healthy.

## 3. A tailnet address and the cloud provider want the same field

ADR-046 invariant 6 requires a routable Tailscale IP on every node that carries
pod traffic, because Cilium derives the VXLAN tunnel endpoint from the node's
`InternalIP` directly. Only the control-plane template implemented it —
`dynamic-node-ip.sh` existed in `KubeadmControlPlaneTemplate` and in neither
`KubeadmConfigTemplate`.

So a CAPI-provisioned worker registered the private address the hcloud CCM
assigns, Cilium built its tunnel on `10.0.0.x`, and home-lab nodes had no route
to it. The failure was partial, which is what hid it: the burst node still
reached pods on the Hetzner control plane over the private network, so cluster
DNS resolved and the node was `Ready`. Only traffic to home-lab nodes failed —
surfacing as a sandbox harness dying with `psycopg ConnectionTimeout` against
`waypoint-pooler`, which runs on a Flatcar worker.

Fixing the address broke the other half. hcloud CCM matches
`alpha.kubernetes.io/provided-node-ip` against the addresses the Hetzner API
reports for that server; a tailnet address is not one of them:

```
error syncing '...-cl7fc-phrlp': failed to get node modifiers from cloud
provider: node address from cloud provider that matches ip: 100.86.202.91,
requeuing
```

CCM then never removes `node.cloudprovider.kubernetes.io/uninitialized`, and
nothing schedules. Two components want different values in one field: Cilium
needs the tailnet address, CCM needs the Hetzner one. Neither is optional and
they cannot be reconciled by choosing.

They are now taken in sequence — register with the address CCM accepts, wait for
the taint to clear, then switch to the tailnet address and restart kubelet, with
a marker file so the kubelet drop-in re-applies it on later starts without
recreating the race.

Two things worth carrying forward. First, the control plane appeared to work and
does not: it has no `providerID` and was never CCM-initialised either — its
`postKubeadmCommands` simply strip the taint with `kubectl taint nodes --all
node.cloudprovider.kubernetes.io/uninitialized-`. The conflict was always
present and invisible, because control-plane workloads tolerate taints anyway.
Burst is the first node where initialisation actually gates scheduling.

Second, `spokepool-worker-bootstrap-*` has the identical gap and is masked by
topology: `default-worker` sits at `replicas: 0` on a hybrid spoke because home
workers fill that role. A pure-Hetzner spoke would have found this the same way.
It is fixed in the same pass rather than left for a different topology to
rediscover.

`86-burst-node-identity.sh` now asserts the ORDER, not just the mechanism, and
resolves the template through the ClusterClass rather than naming a version — a
check that names `-v1` keeps passing against a template nothing is built from,
which is exactly what an immutable-template versioning scheme guarantees will
happen.

## 4. Four ways this ArgoCD reports success while changing nothing

Entry 1 records one. Three more appeared in the same day, and they are worth
listing together because no two share a symptom and all four read healthy:

1. **ComparisonError** — the controller cannot reach repo-server, so it has no
   target state, cannot diff, and auto-sync cannot run. Partial syncs over a
   stale manifest set still report `Succeeded`.
2. **Hook wait against completed jobs** — `waiting for completion of hook
   batch/Job/cm-cert-manager-startupapicheck and 4 more hooks` while those Jobs
   had been `Complete` for eleven minutes. The operation holds at `Running` and
   pins the app to the revision it started on, so a newer commit cannot begin.
3. **Stale cached render** — `op: Succeeded`, `rev: fc39e8a4`, `successfully
   synced (all tasks run)`, and the `syncResult` contained only the templates
   from BEFORE that commit. The commit was on origin and local `kustomize build`
   emitted the new documents; the repo-server served a cached manifest for the
   same revision. A `refresh=hard` immediately followed by a sync does not fix
   it — the sync consumes the pre-refresh cache. The refresh must be observed to
   COMPLETE (its annotation cleared) before syncing.
4. **Partial sync** — `syncResult` covering 3 of the app's 19 resources, each
   reporting `serverside-applied`, with the rest untouched.

The common shape: `status.sync.revision` advances while nothing the revision
introduced reaches the cluster. The field that does not lie is `managedFields` —
server-side apply records when a manager last wrote a field, so an ownership
timestamp older than the commit proves the write never happened, and it proves
it for an object whose diff is currently uncomputable.

A check worth having: an Application whose `status.sync.revision` advances while
its managed objects' `managedFields` timestamps do not is applying nothing,
whatever it reports.

## 5. A ClusterClass literal with no patch over it, next to one with

The spoke control plane would not provision. Every Hetzner server create failed:

```
Ready                  SSHKeyNotFound  ssh key not found in HCloud.
ServerCreateSucceeded  SSHKeyNotFound  SSH key name: zero-ops-mac-mini-debug
```

That key does not exist in the project. The chain from there is mechanical —
no CP server, so `ControlPlaneInitialized=False`, so `InfrastructureReady=False`
("target cluster not ready"), so the Cluster never goes Ready, so the SpokePool
reports `Unready resources: capi-cluster` and the bootstrap times out. 180
attempts over 49m30s, and nothing in that output names an SSH key.

The interesting part is that the HUB class carries the SAME bad literal and was
never affected. It defines an `hcloudSSHKeyName` variable and a `sshKeyName`
patch onto `/spec/template/spec/sshKeys/hcloud/0/name`, so the literal in its
HetznerClusterTemplate is dead text — overwritten before it reaches the API. The
spoke class had the literal and no patch, so what sat in the template was what
shipped.

Two classes, same field, one rendered through a variable and one not. Reading
either file alone tells you nothing is wrong; the fault is only visible in the
difference between them. That asymmetry is the bug, not the key name — a
literal that nothing overrides is a value nobody is reviewing.

The fix mirrors the hub exactly rather than correcting the string, so the two
cannot drift again. Worth a check: any ClusterClass field that one class patches
and another hardcodes.

Note also which template versioning did NOT apply here. `HetznerClusterTemplate`
is immutable, so the reflex is a v4 plus a ClusterClass repoint. That was
unnecessary — `sshKeys` is mutable on the GENERATED HetznerCluster (verified by
server-side dry-run), so the patch alone propagated in about ten seconds and
CAPH retried the server create on its own. No new template, no repoint, no
machine deletion. The immutability constraint governs templates, not the objects
rendered from them, and conflating the two costs a rollout.

## 6. Crossplane held a stale observation after the underlying object recovered

With the CAPI Cluster reading `Ready=True` on every condition, the SpokePool sat
at `Unready resources: capi-cluster` for a further five minutes. The composed
`Object` had `SYNCED=True READY=False`, and its `status.atProvider.manifest`
still carried the PRE-recovery conditions:

```
observed: Ready False, ControlPlaneInitialized False, InfrastructureReady False
actual  : Ready True,  ControlPlaneInitialized True,  InfrastructureReady True
```

`readiness.policy: DeriveFromObject` derives from that observation, so the
SpokePool was faithfully reporting a snapshot that had stopped being true.
Touching the Object's metadata forced a re-observation and both went Ready
within fifteen seconds.

Recording it because the symptom is indistinguishable from a real failure: the
SpokePool says a resource is unready, and the resource is fine. When a composed
Object is `SYNCED=True READY=False`, compare `status.atProvider.manifest`
against the live object before believing either. The provider-kubernetes
DeploymentRuntimeConfig on the hub passes only `--debug`; whether a shorter poll
interval is the right answer was not established — the flag was not verified
against the image, and guessing one crashes the provider.
