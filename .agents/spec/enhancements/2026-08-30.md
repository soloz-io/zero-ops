# 2026-08-30 — hub outage post-mortem observations

A single worker node's kubelet died and the hub was down for roughly six hours.
Nothing in the chain was exotic; every link was a small design choice that only
becomes visible under failure. Recording them here in the order they bit.

## 1. Node-pinned storage makes any node loss unrecoverable

`platform-db` runs one CNPG instance on `local-path`. When the kubelet died the
primary could not reschedule — not "took a while", *could not*, because the volume
exists only on that node's disk. Everything that authenticates against the hub sat
in init behind it.

Worse on rebuild: the PVC and PV objects survive while the directory does not, so
Kubernetes happily binds a claim to an empty path and Postgres starts against a
data directory that isn't there (`stat /var/lib/postgresql/data/pgdata: no such
file or directory`, exit 0, no OOM). The PV's node affinity then pins it to a node
name that no longer exists, and the pod is `Pending` forever.

ADR-046 chose this deliberately and it is defensible for a homelab. What should be
recorded is the actual cost: **one node failure = total hub auth outage + permanent
data loss.** Either replication with network-attached volumes, or accept and
document that the hub data tier has no failover.

## 2. Backups were configured and had never once worked

`barmanObjectStore` is declared on the cluster. No backup has ever completed, so
when the data directory was lost there was no restore point at all. A backup that
has not been restored from is a hypothesis.

Needs: a periodic restore drill into a scratch namespace, and an alert on
`firstRecoverabilityPoint` going stale — not merely on backup *errors*, because
ours never errored, it hung.

## 3. Status conditions used as gates instead of reports

`DatabaseRolesProvisioned=True` gated role provisioning. The database had since
been rebuilt and held only its bootstrap user, but the condition still asserted
the work was done, so the operator skipped it permanently. Nothing would ever have
recovered without a hand-edit.

Fixed for roles (`RoleManager.MissingRoles` — verify `pg_roles`, re-provision when
absent). **`OAuthClientsRegistered` has the identical defect** and is untouched:
Hydra's database was wiped, every client registration gone, condition still True.

Rule worth generalising: a condition records what a controller *did*; it must not
decide whether to do it again.

## 4. Day-0 snapshots that nothing reconciles

Three separate values were written once by the bootstrap CLI and then outlived
what they described:

- `infisical-secrets.DB_ROOT_CERT` — a copy of the CNPG CA. Any cluster rebuild
  regenerates that CA; Infisical then fails its boot migration with
  `SELF_SIGNED_CERT_IN_CHAIN` and crash-loops. **Now reconciled by the operator.**
- `hub-bootstrap-config` — held the pre-wipe Infisical org ID and both project
  UUIDs. Still a Day-0 snapshot; nothing repairs it.
- `infisical-auth` — same class.

`DB_ROOT_CERT` also carries a non-obvious encoding: Infisical wants the env var
base64-encoded, and Kubernetes encodes Secret data again on the wire, so the
stored value is the PEM encoded **twice**. Copying the CA Secret's data field
across verbatim produces bytes that match the CA exactly and still does not work —
this cost an hour. Documented at the reconciler.

## 5. A declared constant counted as a secret producer

`hub-centralized-db-username`/`-password` were declared in `constants.go`,
referenced nowhere, and produced by nothing. `95-infisical-key-producers.sh`
matched the constant declaration and reported the key as produced, so preflight
stayed green. The gap was invisible only because the values happened to survive in
Infisical from an older bootstrap; once that store was reinitialised they were gone.

Fixed: the validator now credits a constant only when its identifier is used
outside its own declaration. The missing producer was added to
`ApplicationSecretMappings`.

## 6. Role provisioning is all-or-nothing

One missing credential (above) meant `RoleManager` could not create
`hub_centralized`, so **no** `hub_*` role was created and the entire auth tier
stayed in init. Consider provisioning roles independently and reporting per-role
status, so one broken credential degrades one service rather than all of them.

## 7. Infisical is a hard dependency of every operator phase

Phase 0 waits for Infisical and blocks everything behind it. A single crash-looping
secrets service therefore held database roles, OAuth clients and all hub
authentication hostage.

ESO-delivered Secrets remain valid in-cluster while Infisical is down, so the
platform can keep running on what is already delivered. Phases should converge
independently with their own conditions rather than in a chain.

## 8. Circular bootstrap dependency between ArgoCD and the secret store

`platform-database`'s sync waits on ExternalSecret health → ExternalSecrets need
Infisical → Infisical needs Postgres → Postgres is the Cluster that sync would
create. A genuine deadlock; broken only by applying the rendered Cluster manifest
directly.

Worth a documented break-glass, or a sync-wave arrangement where the data tier does
not sit behind secret-store health.

## 9. Nothing invalidates a cached copy of another component's key material

Three caches broke and each needed a manual restart:

| Cache | Held stale | Recovered by |
|---|---|---|
| agentgateway JWKS | Hydra's previous signing key | manual restart |
| PgBouncer server cert | pre-rebuild CNPG cert | manual restart |
| Infisical `DB_ROOT_CERT` | pre-rebuild CA | manual patch (now reconciled) |

The JWKS one matters most in production: **Hydra rotating its signing keys is
routine, and it will silently break every ID token validation until someone
restarts agentgateway.** A conforming OIDC client re-fetches the JWKS on an unknown
`kid`; agentgateway appears to fetch once at boot. Fix order: a JWKS refresh
interval if the config supports one; otherwise a Reloader annotation (the idiom
`grafana-alloy` already uses); otherwise document that key rotation requires a roll.

Rotating `agentgateway-oidc-cookie-secret` also invalidates in-flight browser
sessions — PKCE keeps its `code_verifier` in that cookie, so users see "token
exchange failed" until they clear cookies. Expected, but worth stating.

## 10. Resource requests bear no relation to reality

46 of 73 pods declared no memory limit. The scheduler reasoned about 5,456 Mi while
actual demand was 19,577 Mi against 12,288 Mi of capacity — which is why placement
looked fine right up until a kubelet was killed. `metrics-server` was not deployed
at all, so every figure during the incident was inferred from declarations rather
than measured.

Done: `platform-db` bounded (`resources` + `shared_buffers`); `metrics-server`
deployed in place of `prometheus-operator`, which was running with prometheus,
alertmanager, grafana, kube-state-metrics and node-exporter all disabled and no
`ServiceMonitor`/`PodMonitor`/`PrometheusRule` anywhere in the repo — it reconciled
nothing.

Still open: the remaining unbounded pods, and the fact that Kubernetes never
rebalances, so each disruption permanently concentrates load on whichever node had
room at that moment.

## 11. A file on disk that no kustomization references

`sdk/redis/certificate.yaml` existed but was absent from `resources`, so the TLS
Secret was never created and the workload could not start. Resources emitted
together cannot develop that gap — which is one argument for the platform rendering
the tenant cache rather than each fleet hand-writing it.

A CI check that every YAML under a kustomize directory is either referenced or
explicitly excluded would catch the whole class.

## 12. hydra-maester's mint branch leaves orphans nothing reaps

A UUID-named client (`14a848d3-…`) is registered in Hydra from a reconcile where
the referenced Secret was absent. It does not match the `hub-` prefix the
hub-operator's prune uses, so nothing will ever remove it. Each such orphan is a
credential-bearing entry that still authenticates.
