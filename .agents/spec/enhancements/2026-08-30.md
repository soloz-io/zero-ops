# 2026-08-30 — hub outage post-mortem observations

A single worker node's kubelet died and the hub was down for roughly six hours.
Nothing in the chain was exotic; every link was a small design choice that only
becomes visible under failure. Recording them here in the order they bit.

## 1. Node-pinned storage makes any node loss unrecoverable

`platform-db` runs one CNPG instance on `local-path`. When the kubelet died the
primary could not reschedule — not "took a while", *could not*, because the volume
exists only on that node's disk. Everything that authenticates against the hub sat
in init behind it.

Worse on rebuild: the PVC and PV objects survive while the directory does not, so
Kubernetes happily binds a claim to an empty path and Postgres starts against a
data directory that isn't there (`stat /var/lib/postgresql/data/pgdata: no such
file or directory`, exit 0, no OOM). The PV's node affinity then pins it to a node
name that no longer exists, and the pod is `Pending` forever.

ADR-046 chose this deliberately and it is defensible for a homelab. What should be
recorded is the actual cost: **one node failure = total hub auth outage + permanent
data loss.** Either replication with network-attached volumes, or accept and
document that the hub data tier has no failover.

## 2. Backups were configured and had never once worked

`barmanObjectStore` is declared on the cluster. No backup has ever completed, so
when the data directory was lost there was no restore point at all. A backup that
has not been restored from is a hypothesis.

Needs: a periodic restore drill into a scratch namespace, and an alert on
`firstRecoverabilityPoint` going stale — not merely on backup *errors*, because
ours never errored, it hung.

## 3. Status conditions used as gates instead of reports

`DatabaseRolesProvisioned=True` gated role provisioning. The database had since
been rebuilt and held only its bootstrap user, but the condition still asserted
the work was done, so the operator skipped it permanently. Nothing would ever have
recovered without a hand-edit.

Fixed for roles (`RoleManager.MissingRoles` — verify `pg_roles`, re-provision when
absent). **`OAuthClientsRegistered` has the identical defect** and is untouched:
Hydra's database was wiped, every client registration gone, condition still True.

Rule worth generalising: a condition records what a controller *did*; it must not
decide whether to do it again.

## 4. Day-0 snapshots that nothing reconciles

Three separate values were written once by the bootstrap CLI and then outlived
what they described:

- `infisical-secrets.DB_ROOT_CERT` — a copy of the CNPG CA. Any cluster rebuild
  regenerates that CA; Infisical then fails its boot migration with
  `SELF_SIGNED_CERT_IN_CHAIN` and crash-loops. **Now reconciled by the operator.**
- `hub-bootstrap-config` — held the pre-wipe Infisical org ID and both project
  UUIDs. Still a Day-0 snapshot; nothing repairs it.
- `infisical-auth` — same class.

`DB_ROOT_CERT` also carries a non-obvious encoding: Infisical wants the env var
base64-encoded, and Kubernetes encodes Secret data again on the wire, so the
stored value is the PEM encoded **twice**. Copying the CA Secret's data field
across verbatim produces bytes that match the CA exactly and still does not work —
this cost an hour. Documented at the reconciler.

## 5. Role provisioning is all-or-nothing

One missing credential (above) meant `RoleManager` could not create
`hub_centralized`, so **no** `hub_*` role was created and the entire auth tier
stayed in init. Consider provisioning roles independently and reporting per-role
status, so one broken credential degrades one service rather than all of them.

## 6. Infisical is a hard dependency of every operator phase

Phase 0 waits for Infisical and blocks everything behind it. A single crash-looping
secrets service therefore held database roles, OAuth clients and all hub
authentication hostage.

ESO-delivered Secrets remain valid in-cluster while Infisical is down, so the
platform can keep running on what is already delivered. Phases should converge
independently with their own conditions rather than in a chain.

## 7. Circular bootstrap dependency between ArgoCD and the secret store

`platform-database`'s sync waits on ExternalSecret health → ExternalSecrets need
Infisical → Infisical needs Postgres → Postgres is the Cluster that sync would
create. A genuine deadlock; broken only by applying the rendered Cluster manifest
directly.

Worth a documented break-glass, or a sync-wave arrangement where the data tier does
not sit behind secret-store health.

## 8. Nothing invalidates a cached copy of another component's key material

Three caches broke and each needed a manual restart:

| Cache | Held stale | Recovered by |
|---|---|---|
| agentgateway JWKS | Hydra's previous signing key | manual restart |
| PgBouncer server cert | pre-rebuild CNPG cert | manual restart |
| Infisical `DB_ROOT_CERT` | pre-rebuild CA | manual patch (now reconciled) |

The JWKS one matters most in production: **Hydra rotating its signing keys is
routine, and it will silently break every ID token validation until someone
restarts agentgateway.** A conforming OIDC client re-fetches the JWKS on an unknown
`kid`; agentgateway appears to fetch once at boot. Fix order: a JWKS refresh
interval if the config supports one; otherwise a Reloader annotation (the idiom
`grafana-alloy` already uses); otherwise document that key rotation requires a roll.

Rotating `agentgateway-oidc-cookie-secret` also invalidates in-flight browser
sessions — PKCE keeps its `code_verifier` in that cookie, so users see "token
exchange failed" until they clear cookies. Expected, but worth stating.

## 9. Resource requests bear no relation to reality

46 of 73 pods declared no memory limit. The scheduler reasoned about 5,456 Mi while
actual demand was 19,577 Mi against 12,288 Mi of capacity — which is why placement
looked fine right up until a kubelet was killed. `metrics-server` was not deployed
at all, so every figure during the incident was inferred from declarations rather
than measured.

Done: `platform-db` bounded (`resources` + `shared_buffers`); `metrics-server`
deployed in place of `prometheus-operator`, which was running with prometheus,
alertmanager, grafana, kube-state-metrics and node-exporter all disabled and no
`ServiceMonitor`/`PodMonitor`/`PrometheusRule` anywhere in the repo — it reconciled
nothing.

Still open: the remaining unbounded pods, and the fact that Kubernetes never
rebalances, so each disruption permanently concentrates load on whichever node had
room at that moment.

## 10. A file on disk that no kustomization references

`sdk/redis/certificate.yaml` existed but was absent from `resources`, so the TLS
Secret was never created and the workload could not start. Resources emitted
together cannot develop that gap — which is one argument for the platform rendering
the tenant cache rather than each fleet hand-writing it.

A CI check that every YAML under a kustomize directory is either referenced or
explicitly excluded would catch the whole class.

## 11. hydra-maester's mint branch leaves orphans nothing reaps

A UUID-named client (`14a848d3-…`) is registered in Hydra from a reconcile where
the referenced Secret was absent. It does not match the `hub-` prefix the
hub-operator's prune uses, so nothing will ever remove it. Each such orphan is a
credential-bearing entry that still authenticates.

## 12. A readiness gate that does not cover what the process actually needs

auth-proxy's init container is `wait-for-hydra`, and it waits on Hydra's **admin**
port. The first thing the main process then does is a JWKS fetch against Hydra's
**public** port — and treats failure as fatal:

    Performing initial JWKS fetch...
    Initial JWKS fetch failed: ... http://ory-hydra-public…:4444/.well-known/jwks.json: context deadline exceeded

So the gate passes while the dependency the process actually needs is still
warming. Hydra had been up roughly forty seconds; auth-proxy timed out, exited,
and entered backoff.

The blast radius is larger than it looks, because the `auth` HTTPRoute has exactly
one rule — `/` → `auth-proxy:8080`. **Every** path on `auth.dev.nutgraf.in` goes
through auth-proxy, including Hydra's own `/.well-known/jwks.json` and
`/oauth2/token`. While auth-proxy was in backoff the Gateway had no healthy
upstream, the whole auth hostname returned 503, and every OIDC consumer failed its
token exchange against that 503 — which Hydra recorded as fourteen 499s
(client closed request) on the JWKS endpoint, making it look like Hydra was slow
when Hydra was answering in 20ms.

Recovered by restarting auth-proxy once Hydra had settled. Nothing detected or
retried it on its own.

Two fixes, either sufficient:

- Point the init gate at what the process depends on — the public port, ideally
  `/.well-known/jwks.json` itself, not the admin port.
- Make the initial JWKS fetch retry with backoff instead of being fatal. A cold
  start where a dependency is seconds behind is normal, not an error condition.

The second is better: it also covers the case where Hydra restarts later, and it
composes with the JWKS refresh-on-unknown-kid gap recorded in item 9 — both are
the same missing behaviour, one at startup and one at rotation.

Worth noting separately: routing an entire hostname through a single proxy makes
that proxy a hard single point of failure for endpoints it does not own. Hydra's
well-known and token endpoints are unavailable whenever auth-proxy is unavailable,
for reasons that have nothing to do with Hydra.

## 13. Re-provisioning a node destroys its local-path data, and nothing says so

Item 1 records that a rebuild leaves the PVC bound to an empty directory. This is
the mechanism, and the two distinct shapes it takes — both hit the same evening.

`provision-flatcar-worker.sh` creates one VHDX per VM and no separate data disk,
and it recreates that disk unconditionally on every run:

```
Write-Output '    → Creating fresh VM disk from pristine base Flatcar VHDX...'
Copy-Item -Path $baseVhdx -Destination $vhdPath -Force
```

`local-path` stores volumes at `/opt/local-path-provisioner`, on that same disk.
So **re-provisioning any node destroys its local-path data**, on the hub or the
spoke, whatever the node is called. Preserving a node *name* preserves the PV
binding, not the bytes — a distinction that cost an evening to learn, because it
looks like it should preserve both.

Two failure shapes, and the second is the dangerous one:

| | node deleted or renamed | node rebuilt with the **same** name |
|---|---|---|
| PV `nodeAffinity` | points at a node that no longer exists | still matches — valid |
| Storage layer reports | unschedulable | `Bound`, healthy |
| Pod | never starts, `Pending` | starts, mounts an empty dir, dies |
| Observed | hub `platform-db` | spoke `shared-cnpg-1`, CrashLoopBackOff ×63 |

The first fails loudly at scheduling. The second fails at Postgres startup with
`pg_controldata: exit status 1` — no `global/pg_control` — while every layer above
reports success. CNPG shows `Waiting for the instances to become active`; the PVC
shows `Bound`; the node shows `Ready`. Nothing in that chain says "the data is
gone", and the restart counter is the only signal that anything is wrong.

Timeline evidence from the spoke:

```
PV  created:       2026-08-28T06:02:33Z
node re-created:   2026-08-30T15:11:51Z    (same name, pristine disk)
```

Three volumes were lost in one evening this way: `platform-db` (hub),
`shared-cnpg` (spoke tenant database), and `data-platform-redis-0`. Each needed
the PVC deleted by hand so CNPG would provision a fresh one and rebuild via
`initdb` + `postInitSQL`.

ADR-046 §11 documents node pinning as a *placement* constraint — which storage
class binds to which node class. It does not document it as a **re-provision
hazard**, and the provisioner gives no warning before overwriting a disk that
holds bound PersistentVolumes.

Three fixes, in increasing order of cost:

- **Warn and refuse.** Before recreating a disk, have the provisioner check the
  target cluster for bound `local-path` PVs whose `nodeAffinity` names this node,
  and abort unless `--force` is passed. Cheap, and it would have caught all three.
- **Runbook step.** "Take a `pg_dumpall` / CNPG backup before re-provisioning a
  node that holds data" is currently tribal knowledge. It belongs next to the
  provisioning command, not in an incident write-up.
- **A second VHDX.** Attach a separate data disk that the rebuild does not touch,
  and point `local-path` at it. This makes the node genuinely re-provisionable and
  is the only option that removes the hazard rather than guarding it.

The third composes with item 1's larger question: if the data tier is to stay on
node-pinned storage, then the node must be rebuildable without data loss, or the
data must not be node-pinned. Tonight it was neither.

## 14. Infisical project IDs are stored where slugs would do

The ADR-045 generated artifacts carry per-cluster runtime UUIDs:

    manifests/environments/base/generated/hub-bootstrap-config-patch.yaml
      INFISICAL_ORGANIZATION_ID / INFISICAL_PROJECT_ID / INFISICAL_SECRETS_PROJECT_ID
    manifests/hub-core-services/security/generated/infisical-fleet-issuer-patch.yaml
      projectId / clientId

Rebuilding Infisical mints new ones. The committed values then point at projects
that no longer exist, and every folder and secret operation fails with

    Project with 48f3ebf8-… not found

while the configuration looks entirely valid. Correcting the ConfigMap in-cluster
does not survive: it is labelled `argocd.argoproj.io/instance: hub-environment`
and self-heals back to the committed value within minutes — which is exactly the
"a fix applied as a command gets lost" failure. The generated artifacts had to be
updated in Git instead, which is the correct place and worked.

The slugs beside them — `hub-platform`, `hub-secrets`, `dev` — are declared and
stable across rebuilds. Only the UUIDs churn.

**Suggested improvement, deliberately not implemented here.** The operator reads
`INFISICAL_PROJECT_ID` / `INFISICAL_SECRETS_PROJECT_ID` from env at startup
(`cmd/main.go`). It could instead resolve them from the slug against
`GET /api/v1/workspace`, keeping the stored ID only as a fallback and logging when
the two disagree. `internal/client/infisical.go` already has an unexported
`getWorkspaceIdFromSlug` doing exactly this lookup, so the mechanism exists.

That would make a rebuilt Infisical self-correcting rather than requiring a commit,
and it removes a per-cluster identifier from the repository. It was prototyped
during this incident and reverted rather than shipped, because it is a behavioural
change to operator startup and belongs in a reviewed change of its own, not in an
outage.

The same argument applies to `clientId` in the issuer patch, which likewise
identifies a machine identity that a rebuild replaces.

## 15. Rotated client secrets are never revoked

`handleRotation` records the newly minted secret but leaves
`status.clientSecretIDs` empty, and it reads that same field to find the previous
secret to revoke. The result is that every rotation adds a working credential and
removes nothing. Over a few cycles an identity accumulates several valid client
secrets, any of which grants the same access, and none of which appears in the
resource's status.

Observed directly: after the item 16 fix drove a successful rotation,
`clientSecretIDs` was still `[]` while the identity had a working credential.

## 16. A completed PreSync hook Job blocks every future sync of its Application

`sdk-waypoint-sdk-migration` is a PreSync hook carrying
`hook-delete-policy: BeforeHookCreation`. It completed successfully on
2026-08-29T10:35:41Z and was never removed. When CI later published a new SDK
image digest, Git rendered a different podTemplate — and `Job.spec.template` is
immutable, so ArgoCD's dry-run apply was rejected:

    Job/sdk-waypoint-sdk-migration   SyncFailed
      spec.template: ... field is immutable

The dry-run runs before `BeforeHookCreation` gets a chance to delete anything, so
the policy never fires. And because a hook failure aborts the sync before any other
resource is attempted, the *entire* Application stopped syncing. The frontend sat
35 hours behind, and the symptom — "the frontend hasn't synced" — points nowhere
near the cause. The sync result contained exactly one resource, which is the tell.

**This is the mirror of a change made earlier the same day.** `ttlSecondsAfterFinished`
was deliberately removed from this Job (and from the platform migration-job base)
because the TTL controller deleting a Job ArgoCD still had recorded as Running
wedged the sync in the opposite direction: live nil, cached phase Running, the
Application reporting Healthy while the sync never completed. That reasoning was
correct — ArgoCD must be the only deleter. What was missed is that
`BeforeHookCreation` alone does not make ArgoCD delete it in time, so removing the
TTL left the Job to persist indefinitely and become an immutable obstacle.

Suggested fix: `hook-delete-policy: HookSucceeded`. That keeps ArgoCD as the sole
deleter — the property the earlier change was protecting — while ensuring nothing
stale survives to collide with the next render. `BeforeHookCreation` is the wrong
policy for a hook whose podTemplate changes on every image build, because it defers
deletion past the point where the immutability check happens.

Worth checking whether the same combination exists on the platform migration-job
base and on other PreSync hooks: any hook with a mutable-in-Git, immutable-in-API
field has this shape, and it stays invisible until the field actually changes.

## 17. The node-to-node overlay drops packets, and cluster DNS rode over it

Measured from the ArgoCD application controller on `flatcar-hub-node-1`, resolving
an in-cluster name: **7 of 8 lookups succeeded, 1 failed.** Both CoreDNS replicas
were on the Hetzner control-plane node while every workload ran on the home worker,
so every query crossed VXLAN-over-Tailscale.

kubeadm's default is what put them there: `preferred` anti-affinity is a hint the
scheduler may ignore, and CoreDNS tolerates the control-plane taint. Once placed,
nothing re-evaluates it.

UDP DNS does not survive that loss gracefully. The failure surfaced as

    dial tcp: lookup argocd-repo-server on 10.96.0.10:53: no such host

with the Service present, the endpoint ready and the pod healthy — so it read as a
missing service. `tenant-waypoint-dev-workloads` could not generate manifests and
stopped syncing entirely.

**The wider consequence is what makes this worth recording.** Several failures
during this incident were each dismissed as transient and are better explained by
this: the operator's Infisical lookups timing out, the cert-manager DNS-01 solver,
auth-proxy's fatal JWKS fetch at startup (item 12), and intermittent
`i/o timeout` on `platform-db-rw` from the Ory init containers. A resolver that
fails one query in eight produces exactly this pattern — individually plausible,
collectively one cause.

**Addressed** in `manifests/hub-core-services/dns/`:

- `coredns-distribution.yaml` — `required` anti-affinity plus topology spread and
  3 replicas, so no two replicas share a node and each node has a resolver.
  Contributed as scheduling fields only; kubeadm keeps the image and Corefile.
- `coredns-nodelocal.yaml` — NodeLocal DNSCache DaemonSet on 169.254.20.10,
  forwarding to the cluster resolver with `force_tcp`. This is the change that
  removes the failure mode rather than reducing it: the overlay is crossed only on
  a cache miss, and then over TCP where loss is retried by the transport instead
  of returning NXDOMAIN.

**Not yet done, and required for the cache to take effect:** kubelet must advertise
`--cluster-dns=169.254.20.10` on each node. That is a per-node change, applied
after confirming the DaemonSet answers everywhere. Doing it in the other order
points every pod at a resolver that does not exist yet.

A kustomize trap worth remembering from this change: a `patches:` entry whose
target is not also in `resources:` produces no output **and no error**. CoreDNS is
created by kubeadm, so the patch initially rendered nothing while appearing
correct.

Still open: the packet loss itself. Node-local caching makes the platform tolerant
of it, which is right regardless — but a link dropping one packet in eight is a
fault in its own right, and everything that must cross it (pod-to-pod traffic
between hub and home workers, CNPG replication if it is ever distributed) remains
exposed until the path is fixed.

## 18. PostgreSQL 16 broke role management, and the platform has an unrecorded manual grant

Rebuilding a tenant database left Crossplane unable to manage the tenant's role:

    Synced=False ReconcileError
      update failed: cannot update role: pq: permission denied to alter role

`crossplane_admin` holds `CREATEROLE`, which in PostgreSQL 15 and earlier allowed
altering essentially any non-superuser role. **PostgreSQL 16 narrowed this**: a
`CREATEROLE` user may now only alter roles it created, or holds `ADMIN OPTION` on.
After a rebuild, `tenant-waypoint-user` was recreated by something other than
`crossplane_admin` and owned itself, so Crossplane could observe it and not touch
it.

Unblocked in-cluster with

    GRANT "tenant-waypoint-user" TO crossplane_admin WITH ADMIN OPTION;

**That grant exists nowhere in Git.** It will be lost on the next rebuild of this
database, and it does not exist at all for any tenant provisioned in future — so
this will recur silently, presenting as a tenant whose migrations cannot
authenticate.

**Fixed** in the tenant database composition: a provider-sql `Grant` with
`withOption: ADMIN` now makes `crossplane_admin` a member of each tenant role with
admin option, alongside the role's own creation. It is idempotent — where
`crossplane_admin` created the role it already holds this implicitly — so it
repairs the rebuilt case without changing the normal one.

Worth checking whether the CNPG image was recently moved to a PostgreSQL 16 tag,
since this behaviour would have appeared at that point rather than gradually.

## 19. Crossplane reported a role as synced without applying its password

Immediately after item 18 was resolved, the Role resource reported

    Ready=True Available
    Synced=True ReconcileSuccess

while the tenant's migration still failed with `password authentication failed for
user "tenant-waypoint-user"`. The role's password in PostgreSQL did not match the
Secret the resource points at, and the resource asserted success regardless.

The likely mechanism is that provider-sql cannot read a password back — no
database exposes one — so it infers whether an update is needed from the
referenced Secret's resourceVersion. Where the role is recreated underneath it
while the Secret is unchanged, there is nothing for it to notice, and it reports
success having done nothing.

Resolved in-cluster by setting the password directly from the Secret. **That is
also unrecorded**, and it is the second time in one day that a controller's
success condition described work it had not performed — the same family as items 3
and 14, and worth treating as a pattern rather than three coincidences.

This cannot be fixed in this repository — it is the provider's behaviour — so the
**recovery is codified instead**: `scripts/secret/realign-tenant-db-password.sh`
applies the delivered Secret's password to the role, refusing to act if the
ExternalSecret is not synced (applying a stale value would move the role further
from the System of Record). The password is piped on stdin so it reaches neither a
command line nor a log.

Still worth establishing:

- Whether provider-sql offers a way to force reconciliation of the password
  specifically, which would let tenant provisioning do this rather than an
  operator.
- Whether rotating the Secret's value would have triggered it, which would make
  the standing recovery "rotate, do not repair" and remove the script.

And the gap the script does not close: nothing *detects* the divergence. It
surfaces only when a consumer fails to authenticate, with every Crossplane
resource reporting healthy.

## 20. Nothing on this platform can alert, and the collector runs anyway

Item 2 asks for an alert on `firstRecoverabilityPoint` going stale. That request
cannot currently be satisfied by anything, because **no metrics backend is
deployed**. This is the gap underneath several of the items above.

Verified on the hub, 2026-08-30:

```
victoriametrics          0 pods
victoriametrics-alerts   0 pods
clickhouse               0 pods   (platform-billing:  empty namespace)
nats                     0 pods   (platform-messaging: empty namespace)
```

No ArgoCD `Application` exists for any of them either, so they are not pending
deployment — they are manifests in the repo that nothing reconciles. Meanwhile
`grafana-alloy` runs as a DaemonSet on every node, shipping telemetry to a
backend that does not exist. Measured cost of that: **874 Mi across three nodes**
(275 + 270 + 329), on a host that had 699 MB of headroom left. It is the second
largest consumer on the cluster after ArgoCD's application controller.

`metrics-server` was also absent, so during the incident `kubectl top pods` — the
first command anyone reaches for — returned `error: Metrics API not available`.
Every memory figure used to diagnose the outage came from Hyper-V's whole-VM view
or from *declared* requests, and declared requests were shown in item 9 to bear
no relation to reality. Per-pod usage was eventually obtained by scraping each
kubelet directly:

```
kubectl get --raw /api/v1/nodes/<node>/proxy/metrics/resource
```

That works because apiserver→kubelet is a different path from apiserver→ClusterIP,
and it is worth knowing as an incident fallback. When `metrics-server` was later
installed it failed to register anyway — `FailedDiscoveryCheck`, the apiserver
could not reach its ClusterIP — which is a second finding: the observability path
depends on cluster networking that was itself degraded.

### What went unseen because of this

- `ContinuousArchiving=False` on `platform-db` for **days**. The condition was
  there the whole time and no one was watching it (item 2).
- `flatcar-hub-node-1` climbing to **2.2× its memory allocation** with no signal
  until the kubelet died and took the hub with it.
- Two more nodes running over allocation (1.57× and 1.34×) at the same moment.

None of these are subtle. All three are single-expression alerts. The reason none
fired is that there is nowhere for them to fire from.

### Minimum viable, in dependency order

1. **`metrics-server`** — smallest possible step, ~50 Mi, makes `kubectl top`
   work. Not an alerting solution; an incident-response one. Nothing should be
   sized on this cluster again without it.
2. **A metrics backend that is actually reconciled.** Either deploy
   `victoriametrics` behind a real `Application`, or delete it along with
   `victoriametrics-alerts` and stop paying 874 Mi for `grafana-alloy` to ship
   into the void. The present state is the worst of both: full collection cost,
   zero retention, zero query, zero alerting.
3. **Then the rules.** Each of these would have caught a distinct failure tonight:

   - `cnpg_collector_last_available_backup_timestamp` stale > 26h, **and** the
     `ContinuousArchiving` condition being `False` for > 15m. The condition is
     the earlier and sharper signal — archiving broke long before any backup
     window was missed.
   - Node `MemoryDemand / MemoryAssigned > 1.5` sustained. Kubernetes cannot see
     this; it is a hypervisor-level fact, which means the exporter has to run on
     the Windows host, not in the cluster.
   - Any `Node` not `Ready` for > 5m.
   - Any ArgoCD `Application` `OutOfSync` for > 1h — item 16's PreSync deadlock
     retried ten times over 35 hours in silence.

The second rule is the awkward one and worth stating plainly: the failure that
started this outage was **invisible from inside Kubernetes**. The guest kernel
OOM-killed kubelet; from the cluster's point of view the node simply stopped
answering. Only Hyper-V knew that demand had been running at 2.2× allocation for
some time. Any alerting design that only scrapes in-cluster targets will miss
this class of failure again.

## 21. No test asserts that a public hostname refuses plaintext

The tenant TLS chart previously attached one HTTPRoute to both the `:443` and
`:80` listeners with a single proxying rule, so plaintext requests to a tenant
hostname were served rather than redirected. That is fixed, but nothing would
have caught it and nothing would catch its return.

A check that every declared public hostname answers 308 on port 80, and carries
`Strict-Transport-Security` on 443, belongs in preflight. The failure it guards
against is invisible from inside the cluster and presents to a user only as a
browser marking the origin insecure.

The spoke's catch-all `tenant-ingress` route still has no redirect, so any
hostname served by it rather than by `tenant-public-tls` retains the plaintext
behaviour.
