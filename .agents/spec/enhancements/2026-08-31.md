# 2026-08-31 — observations

Continues `2026-08-30.md`. Same rule: one observation per item, recorded in the
order it bit, with the evidence that made it visible.

## 1. Bootstrap assets sit outside GitOps, and drift there is undetectable

`argocd login` could not work over the Gateway. The cause was a missing ALPN
advertisement on the Cilium Gateway listener (item 2). The fix was one word in
`internal/assets/manifests/addons/cilium-rendered.yaml`, committed and pushed —
and the cluster did not change, because **nothing reconciles that file**.

Measured on the hub:

```
ArgoCD Applications: 58
  watching paths under  manifests/ , operators/
  watching internal/    NONE
```

`internal/assets/embed.go` carries `//go:embed manifests`, so that tree is
compiled into the `hub` binary and applied once, during `hub bootstrap`, before
ArgoCD exists. It has to be: the CNI must run before anything can reconcile
anything. But the consequence is a whole class of platform configuration —
Cilium's config among it — that git describes and no controller enforces.

The failure mode is specific and quiet:

```
git         enable-gateway-api-alpn: "true"     (commit b241ecc2, pushed)
cluster     enable-gateway-api-alpn: "false"
ArgoCD      no Application OutOfSync            <- nothing is watching
```

A change can be committed, pushed, pass every pre-commit hook, and have exactly
zero effect, with no signal anywhere that it did not land. The only reason it was
caught is that the change was made *during* an investigation with a live
verification step attached. A routine change to this tree would simply not have
worked, and the next person would debug the symptom rather than the delivery.

There is a second, independent gate that compounds it: `cilium-config` is read by
the Cilium agent **at startup**. Applying the ConfigMap does not reconfigure a
running agent — the DaemonSets must restart. So even hand-applying is two steps,
and on this hub the restart touches four pods (`cilium` ×2, `cilium-envoy` ×2)
carrying all Gateway traffic, which makes it a maintenance-window action rather
than an inline fix.

This is the same class as `2026-08-30.md` item 4 ("Day-0 snapshots that nothing
reconciles"), one layer lower: item 4 is about *values* written once at
bootstrap, this is about the *manifests* written once at bootstrap.

Three remedies, increasing in cost:

- **Detect it.** A preflight or CI check that renders the embedded assets and
  diffs them against the live cluster's corresponding objects. Cheap, and it
  converts silent drift into a failing check. It would have caught this
  immediately, and would also catch drift introduced by hand-editing a running
  cluster — the exact discipline problem this repo already guards against
  elsewhere.
- **Hand off after bootstrap.** Apply the CNI once from the embedded asset, then
  place the same manifests under a `manifests/` path owned by an Application, so
  steady-state ownership moves to ArgoCD and only genesis stays in the binary.
- **Record the procedure.** At minimum, anything touching `internal/assets/`
  needs "rebuild `hub-cli`, verify the embedded value changed, schedule the
  rollout" written next to it. Editing the file is not the change; the binary is.

The rebuild-and-verify step is worth calling out on its own, because it is easy
to skip and silently wrong to skip:

```
strings bin/hub | grep -c 'enable-gateway-api-alpn: "true"'    # 1 after rebuild
strings bin/hub | grep -c 'enable-gateway-api-alpn: "false"'   # 0 after rebuild
```

Before `make build-hub` those counts are reversed. A commit alone leaves the
binary — and therefore every future `hub bootstrap` — on the old value.

## 2. Cilium's Gateway advertises no ALPN, and the error blames the wrong thing

`enable-gateway-api-alpn` defaults to `false`. With it off the Gateway negotiates
no application protocol at all:

```
curl:     ALPN: server did not agree on a protocol. Uses default.  -> HTTP/1.1
openssl:  No ALPN negotiated                                          TLSv1.3
```

Browsers do not care — they fall back to HTTP/1.1 silently, which is why the UI
worked throughout. gRPC clients do care, and the way they fail is misleading.

The argocd CLI probes TLS before connecting. With no ALPN it concludes the
endpoint is not TLS, prints

```
WARNING: server is not configured with TLS. Proceed (y/n)?
```

and on `y` downgrades to `http://`. The Gateway answers plain HTTP for that host
with a 301, which a gRPC POST does not follow, so login dies on

```
POST http://argocd.dev.nutgraf.in/session.SessionService/Create -> 404
```

Every part of that message points somewhere other than the cause. "Not configured
with TLS" is false — the certificate is a valid Let's Encrypt cert and `curl`
without `-k` returns 200. The 404 suggests a routing or path problem. The word
"TLS" sends you to certificates and Gateway listeners, which are all correct.

What isolated it was ruling out the client one flag at a time — `--grpc-web`,
`--plaintext=false`, an explicit `:443`, and omitting `--grpc-web` all failed
identically — and then checking ALPN directly. It was never a flag.

**This is a separate defect from the 307 redirect loop** fixed in `541cc0ae`, and
the distinction matters because the obvious conclusion ("ALPN is the real root
cause, so revert the `server.insecure` workaround") is wrong. They sit on
different legs of the same path:

```
client  --HTTPS--> Gateway  --HTTP--> argocd-server
        ^^^^^^^^^^                    ^^^^^^^^^^^^
        ALPN missing                  307 loop: plaintext to a TLS-mode server
        (breaks gRPC clients)         (fixed by server.insecure)
```

Proven by measurement rather than argument: with ALPN still disabled,
`/api/version` returns **200**. So `server.insecure` fixed the backend leg, and
ALPN has no bearing on it. Reverting `server.insecure` would reinstate the 307
regardless of ALPN. Keeping `argocd-server` TLS-enabled instead is possible —
`BackendTLSPolicy` is available (`v1`, `v1alpha3`, Cilium v1.17.18) — but needs
the route repointed to `:443` plus a policy trusting the self-signed certificate
`argocd-server` generates for itself. That is a separate change with its own
certificate lifecycle, not a revert.

Worth enabling ALPN cluster-wide rather than treating it as an ArgoCD fix: any
gRPC service placed behind this Gateway inherits the same failure, and inherits
the same misleading error while doing so.
